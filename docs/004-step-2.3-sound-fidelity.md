# Step 2.3: sound fidelity (variant selection + gain variation)

Goal: make repeated keystrokes sound less mechanically identical, without
weakening the Step 2.1/2.2 real-time guarantees. Implemented mostly by Codex;
this report covers audit, remaining verification, and sign-off.

## Architecture delta from Step 2.2

Step 2.2 had one `Sample` per category (`click_down`, `click_up`). Step 2.3
widens each category to a fixed 3-slot `SampleCategory` (variants must be
packed from slot 0; trailing empty slots are allowed and treated as absent,
enforced at construction). `SampleBank` is still an array of 2 categories.
`SampleMixer` now also owns a `MixerVariation` (seed + gain range) and
per-category PRNG history (`last_variant_`), on top of the unchanged 32-voice
pool and mixing loop.

## Variant-selection algorithm

Fixed-cost xorshift32 (`random_state_ ^= <<13; ^= >>17; ^= <<5`), seeded from
`MixerVariation::seed`; seed 0 is remapped to 1 in `reset()` so the generator
never gets stuck at the absorbing zero state.

On an accepted Down event with `count` available variants for that category:
- `count == 0`: `Ignored`, no state touched.
- `count == 1`: variant is always 0, no PRNG draw for the pick.
- `count > 1` and no valid previous pick (`last_variant_[cat] >= count`):
  `variant = draw % count` (uniform over all variants — nothing to exclude).
- `count > 1` and a valid previous pick: `variant = draw % (count - 1)`, then
  `if (variant >= last)  ++variant`. This maps the `count-1` non-excluded
  slots onto themselves and the excluded slot onto the last remaining index —
  a direct bijection, not a rejection/retry loop, so the cost is fixed
  regardless of how "unlucky" the draw is.

`last_variant_` is tracked per category (index 0 = A/S/D, index 1 =
Space/Enter), matching the existing per-category trigger mapping. Rejected
events (wrong `KeyEventKind`, unmapped key code) and pool-full events never
call `next_random()` or touch `last_variant_` — confirmed by reading
`handle_event` (the draws happen only inside the `!voice.data` branch found
during the free-slot scan) and by `tests/sample_mixer_test.cpp`'s parallel
`full`/`control` mixer comparison after 64 additional presses following a
pool-full rejection.

## Gain-variation strategy

One extra xorshift32 draw per accepted trigger converts to `[0, 1]` via
`(draw >> 8) / 16777215.0f` (top 24 bits, exact float division), then linearly
maps to `[min_gain, max_gain]` and clamps. Default range is `[0.35, 0.65]`;
`MixerVariation` can only narrow that range (constructor throws
`std::invalid_argument` otherwise) — startup-only, never runtime-configurable.
Each `Voice` stores its own resolved gain; the final mix clamp stays at
±0.8, unchanged from Step 2.2, applied once after all voices are summed.

The range started at `[0.475, 0.525]` (±5%) but was widened to `[0.35, 0.65]`
(±30%, ~5 dB swing) after live listening (see Live verification below) found
the original range imperceptible on a short percussive click. This is a
constant change only; the selection algorithm, PRNG, and RT bounds are
unaffected.

## Pitch strategy: why offline, not in the callback

`_low`/`_high` variants are pre-rendered by `assets/generate_variants.py`
using fixed linear interpolation (source-frame increment 0.92 for low, 1.08
for high — about ±8%, roughly 1.3-1.4 semitones) over the checked-in
`click_down.wav`/`click_up.wav`, written back as 48 kHz stereo PCM16. The
callback (`SampleMixer::mix`) advances voices by whole frames at unity rate;
it does not resample or interpolate. This was a deliberate choice, not a
limitation of the RT path: real-time pitch shifting would need per-voice
fractional-position tracking and interpolation inside `mix()`, adding a
division/multiply and a second sample fetch+blend per output sample on top
of the existing multiply-add — extra work reachable from the audio thread
that buys nothing this project's use case needs, since the sounds are short,
fixed, and known ahead of time. Baking the three pitches into distinct
fixed-length integer-frame buffers keeps `mix()` exactly as simple as Step
2.2's.

The rate was widened from an initial ±3% (0.97/1.03) to ±8% (0.92/1.08)
after live listening found ±3% imperceptible; see Live verification below.

## Real-time safety audit

Read every call reachable from `AudioBoundary::process()` →
`SampleMixer::handle_event()` / `SampleMixer::mix()`, focused on the new
variation code:

| Concern | Reachable? |
|---|---|
| heap allocation / deallocation | No |
| filesystem access | No |
| WAV decoding | No (only at `load_wav_sample`/`load_sample_bank`, startup only) |
| logging | No |
| mutexes | No |
| blocking waits / sleep / condition variables | No |
| unbounded loops | No |
| retry/rejection loops | No (variant exclusion is a direct formula, not a retry) |
| `random_device` or other non-deterministic/syscall-backed RNG | No (xorshift32 is pure arithmetic on a `uint32_t` member) |
| non-trivial local destruction | No (`Voice` is `static_assert`ed trivially destructible; no locals with non-trivial dtors in the hot path) |

`next_random()` is 3 shifts + 3 XORs + a store, fixed cost regardless of
input. Variant selection is a mod, a compare, and at most one increment.
Gain selection is a shift, a cast, a divide-by-constant, a multiply-add, and
a clamp. None of this depends on `count`, the draw value, or prior history in
a way that changes iteration count — all fixed-cost per accepted trigger.

## Callback work bounds (worst case, per `process()` invocation)

Unchanged ceilings: ≤32 events drained (`kMaxEventsPerCallback`), ≤32 active
voices (`kVoicePoolSize`), ≤4096 rendered frames (`kMaxFramesPerCallback`).

- Event drain (≤32 iterations): each iteration does 1 `try_pop`, 3 relaxed
  atomic stores/increments (kind counter, `consumed_total`, `last_code`), and
  one `handle_event` call.
  - `handle_event` worst case: a 32-slot linear scan for a free voice
    (pointer-null checks), plus — only on the iteration that finds a free
    slot — 2 `next_random()` calls (variant draw + gain draw), a mod/compare/
    increment for variant selection, and a shift/cast/divide/multiply-add/
    clamp for gain. Pool-full case: the same 32-slot scan, zero PRNG calls.
  - Totals across ≤32 events: ≤1024 voice-slot scan checks, ≤64 xorshift32
    steps, ≤32 variant selections, ≤32 gain selections, ≤96 kind/consumed
    atomics + ≤32 `last_code` stores + ≤32 started/dropped atomics.
- `budget_exhausted` bump: 1 atomic increment, only when all 32 slots were
  used and the queue may still hold more (deferred, never dropped).
- `mix()`:
  - Silence init: `frames * 2` stores, ≤8192.
  - Per active voice (≤32), per rendered frame of that voice (≤4096), per
    channel (2): 1 multiply + 1 add into the output accumulator — ≤262,144
    multiply-adds worst case (32 voices all active for the full 4096-frame
    window).
  - Final clamp pass: `frames * 2` compares/clamps, ≤8192.

As with Step 2.1/2.2: this is a bound on *operation count*, not a hard
real-time deadline. OS scheduling, page faults, PipeWire's own behavior, and
the compiler's chosen implementation for `std::fill_n` (typically `memset`,
itself not a wait-free primitive on every platform) are outside this
process's control and are not covered by this bound.

## Regression check (Step 2.1/2.2 semantics)

- A/S/D still map to category 0 (`click_down` family); Space/Enter still map
  to category 1 (`click_up` family) — unchanged `switch` in `handle_event`.
- Only `KeyEventKind::Down` triggers playback; `Repeat` and `Up` are counted
  in the boundary counters but return `Ignored` from the mixer and never
  start or stop a voice — a held key still produces one initial sound
  followed by silence (verified by `test_mix`, `test_variant_advancement_and_pool`).
- `input_capture.*` is unmodified — no `EVIOCGRAB` was introduced; foreground
  applications still receive the physical key events.
- Final output clamp is still exactly ±0.8 (`kOutputPeak`), applied once
  after summing all active voices.

## Known limitations

- These are still synthetic development-fixture sounds (short blips), not a
  production keyboard sound library; no license/attribution work has been
  done because no real recorded samples are used.
- Pitch variation is fixed at ±8% and baked at build/asset-generation time;
  there is no runtime pitch control and no more than 3 variants per category
  (`kVariantsPerCategory` is a compile-time constant).
- Variant/gain variety is bounded by a single 32-bit xorshift stream shared
  across both categories; this is intentionally deterministic for testing,
  not cryptographically random, and was never intended to be.
- No perceptual/loudness normalization between the three pitched variants —
  their peak levels are whatever the source WAV plus interpolation produced.
- Even at ±8% pitch / ±30% gain, variation is a coloring effect on a fixed
  short blip, not a different sample; it will still read as "the same click,
  slightly different" rather than truly distinct hits.
