## Architecture and loading

Physical key -> unchanged InputCapture -> unchanged 255-event usable SPSC
transport -> AudioBoundary's 32-event budget -> SampleMixer -> PipeWire PCM.

Main loads two fixed production WAV assets with installed libsndfile before
starting the audio stream. Paths are compiled from the source asset directory
by CMake, so running from another working directory works. This is a development
asset path, not an installation/profile/configuration system.

`load_wav_sample` accepts WAV, exactly 48 kHz, one or two channels, and
1..480,000 frames (ten seconds maximum per sample). It decodes to interleaved
stereo float PCM; mono is duplicated into both channels. Wrong formats, rate,
channel count, empty/oversized samples, decode errors and short reads fail
startup. Non-finite values and PCM outside [-1, 1] are rejected. No resampling.
Prepared PCM is validated again by SampleMixer's startup constructor; empty
bank slots are allowed for silent boundary tests. Production must load both files.
Maximum decoded bank storage is 7,680,000 bytes. Actual assets contain 1,681
and 1,201 stereo frames: 23,056 bytes of decoded PCM total.

AudioBoundary owns SampleMixer, which owns an immutable two-sample bank.
Each of 32 preallocated voices contains only a pointer, frame count and cursor.
Only the PipeWire callback accesses running voices. Startup publishes the
prepared data before callbacks can run. Stop destroys the stream and stops
the thread before resetting voices; sample vectors are destroyed later on the
owning thread. Restart cannot resume an old voice.

## Playback policy

| Physical code | Press (`Down`) | Repeat | Release (`Up`) |
| --- | --- | --- | --- |
| A / S / D | Start click_down.wav | Count only | Count only |
| Space / Enter | Start click_up.wav | Count only | Count only |
| Other keys | Count only | Count only | Count only |

No character reconstruction or device grabbing. Releasing a key does not
cut off its sound. Holding one key produces one sound; kernel repeats do
not retrigger it. Distinct presses, including rapid presses of the same key,
start independent voices at frame zero. Events consumed in the same callback
start together at that buffer's first frame; timestamps are not used for
within-buffer scheduling.

The first free voice slot wins. With all 32 occupied, **drop the newest sound
trigger**, leaving every playing voice untouched. There is no pending-sound
queue and no voice stealing. The event itself is still consumed and counted.
`voices_dropped` counts this case separately from transport `dropped_count`.
At most 32 events are removed per callback; remaining events stay in transport.
Triggers are handled before mixing; a voice that finishes later in this buffer
is still occupied when that buffer's triggers are handled.

For each buffer, clear output to silence, add each active voice at **0.5 gain**,
then clamp the final sum once to **[-0.8, +0.8]**. Clamping after all voices
preserves positive/negative cancellation before clipping. Valid samples limit
the pre-clamp sum to [-16, +16], so float overflow and NaN cannot arise from
this arithmetic. No compressor, limiter or other DSP. Clipping can distort
dense chords; a digital peak cap is not a guarantee about physical loudness.

Advance each voice by exactly min(output frames, remaining sample frames).
Retire at the exact end, reset the whole trivial voice record, and leave the
rest of the buffer silent for that voice. Reuse starts at zero with the new
sample's length and pointer.

## Callback bounds and RT audit

Let F be min(buffer byte capacity / 8, nonzero requested frames, **4096**).
A zero request means use capacity, still capped at 4096. Requests are compared
before narrowing. The explicit frame ceiling supports usual 128..4096 frame
development quanta while preventing unexpectedly large server buffers from
creating an excessive callback loop. Larger requests get a shorter chunk;
voices advance only for submitted frames. Graphs needing more than 4096 frames
per callback are outside this slice's supported range and can underrun.

Per callback maximum:

- 32 event copies/dispatches, regardless of concurrent producer activity.
- 32 active voices; at most 32 x 32 = 1,024 slot inspections for triggering.
- 32 voice inspections for mixing.
- 32 x F x 2 sample multiply/add contributions: at most **262,144**.
- 2F silence writes and 2F final clamps: at most **8,192 each**.
- 32 cursor updates/retirements. No retries or producer-dependent loops.

All application atomic operations reachable from `process()`:

| Object | Type | Operation and ordering |
| --- | --- | --- |
| Queue tail | size_t | relaxed load, release store on successful pop |
| Queue head | size_t | acquire load |
| presses / releases / repeats | uint64_t | one relaxed fetch_add per valid event |
| consumed_total | uint64_t | relaxed fetch_add per event |
| last_code | uint16_t | relaxed store per event |
| voices_started OR voices_dropped | uint64_t | at most one relaxed fetch_add per event |
| budget_exhausted | uint64_t | relaxed fetch_add if 32 events consumed |

Worst case: **225 atomic operations** (32 x 7 + 1). An unsuccessful pop
uses two loads; a callback with fewer than 32 events stays below that bound.
Existing compile-time always-lock-free assertions cover size_t, uint64_t and
uint16_t on the supported Linux x86-64 target. No new atomic type was added.
The mixer itself uses no atomics. Transport drops and main's signal flag are
not accessed from this callback. Counters publish no sample data; relaxed
ordering is sufficient for independent observations. Queue synchronization
and single-producer/single-consumer ownership remain as audited in Step 2.1.

Application allocations/deallocations reachable from the callback: **none**.
No decoding, loading, file I/O, log output, mutex, condition variable or wait.
Vector operations there are read-only empty/size/data access to the immutable
bank. Array indexing, min/clamp, scalar arithmetic and bounded fill have no
allocating behavior. No local owner or non-trivial destructor runs there.
Event and voice values are trivial. `process`, its entry point, event handling
and mixing are noexcept and have no throwing operations.

Release object-code inspection confirms the normal external calls are:

- `pw_stream_dequeue_buffer` and `pw_stream_queue_buffer`: explicitly marked
  **RT safe** in installed PipeWire 1.6.8 `pipewire/stream.h`, lines 614..619.
- `memset`, emitted for std::fill_n: a bounded write of at most 32,768 bytes.
  It has no general hard-deadline promise; this audit relies on the installed
  libc implementation's ordinary memory-fill behavior. The other C++ helpers
  inline; no libsndfile call is reachable.

The compiler also emits `__stack_chk_fail` only for detected stack corruption;
it is an abnormal fatal path, not a valid playback operation. Application
dynamic symbols are resolved at startup (`-z now`) to avoid first-call lazy
linker work in the callback. PipeWire internal behavior remains covered by
its RT API contract, not by inspection of every library instruction.

These are operation and ownership bounds, **not proof of a hard wall-clock
deadline**. OS preemption, paging and audio-driver behavior still apply.
Memory is loaded/touched at startup but not locked against paging.
