# 002 — Step 2.1: Production Input → Transport → Audio Boundary

Status: implemented. Independent audit: automated checks and live physical
press/release/repeat consumption passed (see final live verification below).
Builds on the completed feasibility spike in `docs/001-core-feasibility-spec.md`; assumes no more
than that spike actually proved.

## Scope

The first production slice only:

```
physical keyboard event -> production input capture -> bounded transport -> PipeWire audio callback
```

No sample selection, mixing, voices, or audible output exist yet — the
audio callback outputs silence and only proves the transport boundary via
counters. Code lives in `src/` at the repo root (`CMakeLists.txt` builds
it as target `keeby`); `experiments/input-reader/` is untouched, kept as
the frozen Step 1.4 spike.

## Production event flow

```
InputCapture (std::jthread)
  libevdev, O_RDONLY, never EVIOCGRAB'd, EVIOCSCLOCKID(CLOCK_MONOTONIC)
  -> classify_key_value(ev.value) -> KeyEvent{code, kind, ts_ns}
  -> KeyEventTransport::try_push()          [non-blocking, bounded]

AudioBoundary::process()  (PipeWire real-time thread, not owned by us)
  -> KeyEventTransport::try_pop() up to 32 times per callback  [bounded]
  -> update AudioBoundaryCounters (atomics only)
  -> write silence to the output buffer
```

## Thread ownership

- **Input-capture thread**: a `std::jthread` owned by `InputCapture`,
  using `std::stop_token` for cooperative shutdown (`poll()` with a
  200ms timeout plus stop checks inside event draining; OS scheduling can add delay). Owns
  the device fd and `libevdev*` for its entire lifetime; both are
  released when the thread exits.
- **PipeWire real-time thread**: owned and scheduled by PipeWire itself
  (`pw_thread_loop`), not by our code. We only supply the `process()`
  callback.
- **Main thread**: constructs the shared `KeyEventTransport`, starts
  `AudioBoundary` then `InputCapture`, waits for a shutdown signal, stops
  both (capture first, then audio), and is the only thread that reads
  counters or prints anything.

## Queue/transport choice

`EventTransport<T, StorageSlots>` (`src/event_transport.hpp`): a hand-rolled
bounded single-producer/single-consumer lock-free ring buffer (atomic
head/tail, acquire/release ordering), the same proven pattern from the
Step 1.4 spike, now with the dropped-event counter built into the type
itself rather than tracked externally.

This deliberately does not reach for an established third-party
lock-free-queue library. Considered: Boost.Lockfree's `spsc_queue` (only
`boost-libs`, the compiled runtime, is installed on this machine — the
`boost` headers package is not, so using it means another `sudo pacman
-S boost`) and `moodycamel::ReaderWriterQueue` (not packaged at all;
would mean vendoring an unvetted single header from the internet
straight into the keylogger-adjacent input path). The existing
implementation is a ~30-line textbook SPSC ring, already unit-tested
(`tests/event_transport_test.cpp`), and already validated live at zero
drops across roughly 1,000 real key events in Step 1.4. That is treated
as the "strong technical reason" to keep it rather than add a new
dependency for this step; revisit if a future step's throughput
requirements outgrow it.

- **Usable capacity**: 255 events in 256 backing slots; one slot is
  reserved to distinguish full from empty. `capacity()` returns 255.
  The backing-slot count must be a power of two for mask-based modulo. Carried over unchanged from Step 1.4, where it was never
  observed to drop a single event under real, sustained typing,
  including rapid typing and multi-second repeat bursts.
- **Overflow policy**: drop-newest. If `try_push` finds the buffer full,
  it discards the incoming event and atomically increments the
  transport's own `dropped_` counter — it never blocks the producer and
  never overwrites an unconsumed slot.
- **Dropped-event instrumentation**: `EventTransport::dropped_count()`,
  a relaxed atomic load, safe to call from any thread at any time. Not
  currently exported to metrics/logging — read once at shutdown in this
  step's verification executable (`src/main.cpp`). Wiring it into
  ongoing observability is future work.

## Real-time-thread restrictions

Applies to `AudioBoundary::process()`, which runs on PipeWire's real-time
thread:

- no heap allocation (no `new`, no growing container);
- no blocking synchronization (no mutex/condvar — the transport's ops
  are lock-free/wait-free);
- no filesystem access;
- no console/stdout/stderr logging (diagnostics go into
  `AudioBoundaryCounters`, atomics readable from any other thread
  instead);
- no blocking channel operations (`try_pop` is wait-free and the drain
  loop has an explicit 32-event budget, independent of producer activity);
- no unnecessary cloning (the one copy per event, a 16-byte POD out of
  the ring buffer, is unavoidable and cheap for a lock-free SPSC queue);
- no exception/panic paths (nothing in this function can throw; PipeWire's
  C API reports failures via return codes);
- no destruction of non-trivial objects.

This is enforced by code review and an inline audit comment directly
above `process()` in `src/audio_boundary.cpp`, not by a static analyzer
— no such tool is configured in this repository yet.

## Known limitations

- Single-keyboard capture only; `KeyEvent` has no device-identity field,
  so a second concurrently-captured keyboard would be indistinguishable
  from the first (documented as an explicit assumption in
  `src/key_event.hpp`).
- Device discovery is still "first match wins" over `/dev/input/event0..31`.
- No hot-unplug re-enumeration: a disconnect is detected and the capture
  thread exits, but nothing retries or re-discovers.
- `dropped_count()` is read once at shutdown by the verification
  executable, not continuously monitored; under materially higher event
  rates than tested here, it should be sampled periodically instead.
- No sample playback, mixing, or voices exist yet — silence only. Do not
  read anything about audible latency into this step; the 128-frame
  PipeWire quantum and ALSA buffer figures measured in Step 1.4 are not
  re-validated or re-claimed here.
- No production permission model beyond what Step 1.4 already flagged as
  unresolved (see `docs/001-core-feasibility-spec.md`, Permissions
  section) — this step relies on the same pre-existing `input`-group
  membership, not a newly designed scheme.

### SPSC synchronization and capacity

The capture thread is the only producer/head writer; the PipeWire process
callback is the only consumer/tail writer. Queue initialization happens
before either thread starts. Main stops capture before audio and destroys
transport last. Sequential tests may transfer roles after thread joins.

Producer writes a whole slot before releasing head. Consumer acquires head
before reading that slot, so it cannot see a partially written event.
Consumer finishes the copy before releasing tail; producer acquires tail
before reusing storage, so overwrite cannot race that copy. A full push
returns before writing any slot or moving head: exactly drop-newest.

Only each thread's own index load is relaxed. Peer index observations use
acquire; index publication uses release. Atomic coherence and the reserved
slot prevent either participant from lapping the other; stale observations
can cause a failed push/pop but cannot authorize premature slot access.
Indices stay in 0..255. Masked wraparound never approaches size_t overflow.
**256 backing slots hold exactly 255 queued KeyEvents.** The production-size
capacity test fills all 255, rejects the next event, and checks every payload.

The producer alone increments the uint64_t dropped counter using relaxed
fetch_add. Main reads it after shutdown; any monitoring thread may use its
relaxed load concurrently. This counter does not publish payload data.
Values are independent snapshots, cumulative modulo 2^64. Audio counters
are likewise individual snapshots, not one coherent group during execution.

Reference for the language rules: [C++ memory model](https://eel.is/c++draft/intro.races)
and [atomic ordering](https://eel.is/c++draft/atomics.order).

### Callback atomics and work bound

All application-owned std::atomic operations reachable from process():

| Object | Type | Operation/order |
| --- | --- | --- |
| transport tail | size_t | load relaxed; successful pop stores release |
| transport head | size_t | load acquire |
| presses/releases/repeats | uint64_t | one relaxed fetch_add per event |
| consumed_total | uint64_t | relaxed fetch_add per event |
| last_code | uint16_t | relaxed store per event |
| budget_exhausted | uint64_t | relaxed fetch_add when 32 events consumed |

On this Linux x86-64 target (GCC 16.2.1), existing is_always_lock_free
assertions passed for all three types. A runtime is_lock_free probe also
returned true for size_t, uint64_t, and uint16_t. The dropped counter is
lock-free too, but is not accessed by process(). PipeWire internals are an
external library boundary; installed PipeWire 1.6.8 stream.h explicitly
marks dequeue_buffer and queue_buffer RT safe.

**At most 32 events are consumed per callback**, including with a continuously
active producer. A while(try_pop) loop alone could run indefinitely despite
finite capacity. The preserved explicit budget prevents that. Leftover
events stay queued; reaching the budget does not drop them. With no new
arrivals a full queue takes eight callbacks. At the cap there are 193
application atomic operations (6 per successful pop/event plus one budget
counter increment). Silence filling is bounded by the supplied buffer's
maxsize and requested frame count. These are operation bounds, not a measured
hard real-time deadline: scheduling, paging and library internals still matter.

### Remaining limits

Physical press/release/repeat verification passed in the final run below.
SPSC ownership is
an API contract, not a multi-producer guard. This is a single Linux x86-64
host check, not proof for other architectures or hard deadline performance.
Transport saturation deliberately loses newest events. Existing evdev sync
recovery discards synchronization events, and kernel overruns are not counted
by the transport counter; this is not a lossless key-state model for a future
mixer. Shutdown may leave pending queue events unconsumed. Device discovery,
hotplug, asynchronous PipeWire error reporting and permission design remain
as scoped limitations. TSAN and finite stress tests do not replace the memory
ordering argument. No mixer or Step 2.2 functionality was added.
