# Step 2.5: security/permissions architecture for keyboard access

## 1. Goal

Define the minimum-safe Linux permissions boundary for KEEBY's keyboard
access in production: no full-application root, no unnecessarily broad
*permanent* privilege, KEEBY unable to write to or exclusively grab the
keyboard, and a clear, evidence-based answer to how an ordinary desktop
user should obtain that access under Wayland/Niri.

## 2. Previous security problem

None was introduced by KEEBY's own code — Steps 2.1-2.4 already open the
device `O_RDONLY`, never call `EVIOCGRAB`, never write to the device, and
never request elevated privilege. The problem this step addresses is
**environmental**: KEEBY currently works only because the logged-in user
already happens to be a permanent member of the system's `input` group —
state that predates this project and was not set up by it — which grants
raw read access to *every* `/dev/input/event*` device to *every* process
that user ever runs, not just KEEBY. That is broader than KEEBY needs, and
is exactly the risk this step's threat model calls out.

## 3. Threat model

As given, plus one documented deviation from the given assumptions:

- Raw keyboard events are confidentiality-sensitive (passwords, codes,
  terminal commands) — treated as such throughout.
- KEEBY needs read-only access to exactly one keyboard device; no write,
  no injection, no `EVIOCGRAB`.
- Running all of KEEBY as root, or setuid-root, is unacceptable/high-risk.
- Permanent `input`-group membership is potentially over-broad and must not
  be accepted without explicit analysis (done below — section 6).
- **Deviation from the task's framing**: the task's assumptions describe
  `input`-group membership as something KEEBY might *grant*. On this
  machine it is **pre-existing, not something KEEBY sets up or could
  meaningfully "avoid granting"** — the user (`yahiro`) was already in
  `input` (gid 992) before this project existed. This report treats that
  pre-existing fact as the *current, already-in-place* mechanism to
  evaluate and report on, not something Step 2.5 is choosing to add.

## 4. Current device-access audit

Answering the task's ten required questions, from the live system and
`src/input_capture.cpp`/`.hpp` as of the start of this step:

1. **Which devices**: `discover_keyboard_device()` scans
   `/dev/input/event0`..`event31`, opening each `O_RDONLY | O_NONBLOCK` and
   checking `libevdev_has_event_code` for `KEY_A`, `KEY_Z`, `KEY_SPACE`,
   `KEY_ENTER` (a "looks like a full keyboard" heuristic); the first match
   is used. On this machine that is `/dev/input/event3` (AT Translated Set
   2 keyboard).
2. **Open flags**: `O_RDONLY | O_NONBLOCK`, both in discovery and in
   `InputCapture::start()`. Already minimal for this step's requirements —
   no code change was needed here.
3. **Read-only or read-write**: read-only. Confirmed by flags and by
   `capture_loop` never calling any write-class evdev/ioctl (only
   `libevdev_next_event`, `poll`, and — once, at startup —
   `EVIOCSCLOCKID`, which sets the *reader's own* fd-local timestamp clock
   and does not write to the device's shared state).
4. **`EVIOCGRAB`**: never used — confirmed by the explicit comment at
   `input_capture.cpp:151` and by code inspection; no `libevdev_grab` call
   exists anywhere in the codebase.
5. **One keyboard or multiple**: one — `discover_keyboard_device()` returns
   the first match only; `InputCapture` owns exactly one fd/thread.
6. **Discovery**: static scan of `/dev/input/event0..31` at startup only
   (or an explicit path via `argv[1]`); no udev/inotify-based enumeration.
7. **Hot-plug/reconnect**: not supported before this step. A device that
   disappears after startup silently ended the capture thread with no
   surfacing anywhere (see section 15 for the small, non-privileged fix
   made in this step); a keyboard that appears *after* startup is never
   discovered (no rescan).
8. **Running user**: verified live — `uid=1000(yahiro) gid=1000(yahiro)`,
   not root. A running instance was also checked directly:
   `Uid: 1000 1000 1000 1000`, `Gid: 1000 1000 1000 1000` (real, effective,
   saved, filesystem all 1000), `CapEff: 0000000000000000`,
   `CapPrm: 0000000000000000` — zero effective or permitted Linux
   capabilities of any kind.
9. **Device permissions/ACL**:
   ```
   $ ls -la /dev/input/event3
   crw-rw---- 1 root input 13, 67 ... /dev/input/event3
   $ getfacl /dev/input/event3
   # owner: root
   # group: input
   user::rw-
   group::rw-
   other::---
   ```
   Mode `0660`, owner `root`, group `input`. **No extra ACL entries** —
   critically, no `user:1000:rw-` entry, which is what systemd-logind adds
   dynamically for `uaccess`-tagged devices. Its absence here is evidence,
   not just a claim (see point 10).
10. **Why access currently succeeds**: verified to be **static `input`
    group membership**, not logind/seatd ACL:
    - `groups` for the user includes `input` (gid 992).
    - `getfacl` on the device shows no session-added ACL entry (point 9).
    - `systemctl is-active seatd` → `inactive` (seatd is not running on
      this machine at all).
    - `udevadm info -q property /dev/input/event3` shows
      `TAGS=:power-switch:` only — **no `uaccess` tag**.
    - Reading `/usr/lib/udev/rules.d/70-uaccess.rules` directly (systemd's
      own stock ruleset, unmodified) shows exactly one rule touching
      `SUBSYSTEM=="input"`:
      `SUBSYSTEM=="input", ENV{ID_INPUT_JOYSTICK}=="?*", TAG+="uaccess"`
      — **joysticks only**. Neither `70-mouse.rules` nor
      `70-touchpad.rules` grants `uaccess` either (checked directly; both
      only do hardware-database classification, no ACL/TAG grant).
    - **Conclusion, evidence-based, not assumed**: on this system —
      representative of any distribution shipping systemd's stock rules
      unmodified — **systemd-logind's per-session `uaccess` ACL does not
      apply to keyboards, mice, or touchpads at all**, only to joysticks.
      Access here is 100% attributable to the pre-existing `input` group
      membership; no root execution, no manual ACL, no udev rule specific
      to this device, and no logind/seatd session mechanism is involved.

## 5. Approaches evaluated

### A. systemd-logind / active-session device access — **does not apply, verified**
Investigated directly (section 4, point 10) rather than assumed. Stock
systemd's `uaccess` mechanism explicitly excludes generic keyboards
(deliberately — see the rule comment context: only joysticks, plus a
narrow list of other device classes like cameras/scanners/smartcards, get
this treatment). **Rejected as unavailable**, not merely undesirable: there
is no session-scoped ACL currently granting this access, and enabling one
would require the same kind of custom udev-rule change evaluated in B.

### B. udev ACL/rule-based access — **evaluated, rejected as currently proposed**
A custom rule adding `TAG+="uaccess"` for keyboard-classed input devices
(e.g. `SUBSYSTEM=="input", ENV{ID_INPUT_KEYBOARD}=="1", TAG+="uaccess"`)
would let logind grant a *session-scoped*, auto-revoked-on-logout ACL entry
instead of a permanent group. This is a genuine improvement in one
dimension (time-boundedness) but **not in the dimension the task cares
about most** ("whether the rule would expose raw input to every local
process owned by that user" — yes, unchanged: a `uaccess`-style ACL is
per-UID, exactly like group membership, so it grants access to *every*
process that UID runs, not to KEEBY specifically). It also reverses a
choice systemd upstream deliberately made (excluding keyboards from
`uaccess`), which this report treats as a considered security decision
worth respecting rather than quietly overriding. A mode-based rule
(`MODE="0666"` or similar world-readable grant) was never seriously
considered — the task correctly flags this as unacceptable, and it is
strictly worse than the status quo. **Not selected** as the recommended
production mechanism, for the reasons above; noted as a documented
alternative.

### C. `input` group — **analyzed; this is the current, pre-existing mechanism**
Access is currently provided this way (section 4). Consequence: **every
process the logged-in user runs — not only KEEBY — can already read every
`/dev/input/event*` device**, including any other keyboard, mouse, or
future device on the system, for as long as that group membership exists
(indefinitely, until explicitly revoked). This is the exact
over-broad-and-permanent risk the task's threat model names. It is not
something this step is introducing, but continuing to *rely on* it as
KEEBY's long-term answer would fail the task's stated goal ("without
granting unnecessarily broad permanent privileges").

### D. Privileged helper process — **the only approach that actually narrows scope; requires the decision checkpoint (section 7)**
A tiny, separate process that owns only device-open + evdev-read, forwarding
bounded, fixed-size messages to the unprivileged main KEEBY process over a
local, filesystem-permission-restricted Unix domain socket. Unlike B/C,
this can plausibly let the **interactive user's account leave the `input`
group entirely**, with only one small, auditable, single-purpose binary
retaining device access (see section 7 for exact proposed shape). This is
the direction the task's own architecture section clearly anticipates.
**Not implemented in this step** — see section 7.

### E. Direct device FD delegation — **evaluated as a variant of D, same checkpoint**
A trusted component (e.g. a udev-triggered systemd service, or a
polkit-mediated helper) opens the device once and passes the FD via
`SCM_RIGHTS` to KEEBY, rather than forwarding a continuous event stream.
This removes the "privileged process runs for the app's whole lifetime"
property of D, trading it for "the unprivileged process directly holds a
raw fd to a security-sensitive device thereafter" — a different, not
obviously smaller, risk (the fd itself becomes something to protect against
leaking via `fork()`/`exec()` without `O_CLOEXEC`, accidental duplication,
etc.). Also requires the decision checkpoint if selected; not chosen over D
in this report because D keeps the *smallest possible* amount of
long-lived code with device access, and FD delegation does not remove that
requirement — it only changes where the still-necessary open() call lives.

### F. setuid/setcap — **evaluated, rejected**
- **setuid root** on the whole `keeby` binary: rejected outright per the
  task's own instruction and by any reasonable least-privilege analysis —
  the binary also links PipeWire, sdbus-c++, and libsndfile, a large
  dependency/attack surface to run privileged even momentarily.
- **File capabilities** (e.g. `cap_dac_override` or similar) on the whole
  `keeby` binary: rejected for the same reason — capabilities that apply to
  the *entire* process for its *entire* lifetime are not meaningfully
  narrower than setuid for a binary this size, and Linux capabilities do
  not map cleanly onto "open one specific character device class" anyway
  (there is no `CAP_OPEN_EVDEV`; the closest broad capabilities like
  `CAP_DAC_OVERRIDE`/`CAP_DAC_READ_SEARCH` bypass *all* file permission
  checks, which is far broader than the one device access needed).
- A **setgid-`input` bit on a small, separate helper binary** (not the
  whole app) is a narrower variant of F that is architecturally identical
  to option D's privilege *source* (see section 7) — evaluated together
  with D, not as a separate rejected option.

## 6. `input`-group security consequences (explicit analysis, as required)

Membership in `input` grants read (and on `crw-rw----` devices, write —
though writes are only meaningful for devices that accept them, e.g.
`uinput` or LED-control ioctls on some keyboards) access to **every**
`/dev/input/event*` node on the system for **every** process the member
user runs, for as long as the membership exists. On this machine, that
currently includes at minimum the internal keyboard and whatever other
input devices `ls /dev/input/` lists (mice, touchpads, etc. — not
enumerated further here per the instruction not to paste unnecessary
system data). A malicious or compromised *unrelated* process running under
this user account — a browser extension, an `npm install` postinstall
script, anything — already has, and would continue to have, the same raw
keyboard-read capability KEEBY uses, entirely independent of whether KEEBY
exists at all. **This is a pre-existing property of the machine's current
configuration, not a KEEBY-introduced risk** — but it is exactly the
condition the task says must not be accepted "without explicit security
analysis," which this section provides.

## 7. Decision checkpoint — STOP, no implementation past this point

Per the task's explicit instruction, implementing any of the following
requires stopping for approval before writing code: setuid root, a root
daemon, executable capabilities, permanent `input`-group membership,
world/group-wide device permission changes, a polkit policy, a privileged
systemd service, or a custom privileged helper. The only architecture in
sections 5-6 that actually narrows privilege below the status quo — a
privileged helper (D) — falls squarely in that list. **This report stops
here rather than implementing it.**

**1. Why the simpler options failed:**
A (logind uaccess) does not apply to keyboards at all on stock systemd —
verified, not assumed. B (custom uaccess rule) and C (the pre-existing
group) both grant access to every process the user runs, not to KEEBY
specifically — neither is actually narrower than the status quo in the
dimension that matters for a "raw keyboard events are sensitive" threat
model; B only adds time-boundedness. F (setuid/capabilities on the whole
app) is broader than necessary for a binary that also links PipeWire,
D-Bus, and a sound-file library. Only a process-separated helper (D) can
plausibly let the interactive user's account stop needing `input` group
membership at all.

**2. Proposed privilege architecture:**
A new, separate, minimal executable (e.g. `keeby-input-helper`, on the
order of 100-150 lines, no new library dependencies beyond what
`input_capture.cpp` already uses — libevdev only) whose entire job is: open
the discovered keyboard device read-only, read evdev events, and forward a
fixed-size, versioned `KeyEvent`-shaped message over a `SOCK_SEQPACKET`
Unix domain socket created under `$XDG_RUNTIME_DIR` (already mode `0700`,
per-user) to the main `keeby` process, which connects to it instead of
calling `InputCapture::start()` directly. The helper file is owned
`root:input` with the setgid bit set (`chmod 2750 root:input
keeby-input-helper` conceptually); the **interactive user's account is no
longer a member of `input`** — only this one binary can open evdev nodes.
`EVIOCGRAB` is still never called; the helper remains a passive observer.

**3. Exact privilege being granted:**
Setgid `input` on one ~100-150 line binary whose only externally-reachable
behavior is: open a device path it discovers itself the same way
`discover_keyboard_device()` already does, read events, and write
fixed-size structs to a socket already connected by its (also
unprivileged) parent/peer. It does not accept a device path as untrusted
external input beyond what today's `argv[1]` already allows, does not
execute other programs, does not touch the filesystem beyond the one
device path and the one socket, and links no networking, PipeWire, D-Bus,
or sound-decoding code (matching the task's explicit exclusion list for a
privileged component).

**4. Attack surface introduced:**
One new process, one new local IPC channel (a `SOCK_SEQPACKET` socket under
a `0700` per-user runtime directory — not network-reachable, not
world/group-accessible by construction), and one new small codebase that
must be kept simple enough to audit (the task's own requirement: "treat its
inputs as untrusted," "unbounded IPC messages," "malformed IPC input
rejected" all become real review items for this helper specifically, not
present at all today). A compromise of the *unprivileged* main KEEBY
process (which is far larger — PipeWire, sdbus-c++, libsndfile) would no
longer, by itself, grant raw keyboard read access to whatever compromised
it, which is the actual security improvement over the current `input`-group
status quo.

**5. Alternatives considered:** A (rejected, inapplicable), B/C (rejected,
not actually narrower — section 5), E (FD delegation — considered
architecturally similar but does not remove the same amount of code from
running with device access on an ongoing basis), F (rejected, too broad
for this binary's size).

**6. Installation impact:** Requires one explicit, visible privileged
install step (setting ownership/setgid on the helper binary, e.g. via a
small install script the user runs with `sudo` once, or a packaged
`postinstall` step) and, if the user's account should stop being a member
of `input`, a separate explicit `sudo gpasswd -d $USER input` the user
would need to run themselves and understand (removing a group membership
can affect other unrelated software also relying on that group — this must
be the user's own informed choice, never done silently by an installer).
No `sudo` would be needed to *launch* KEEBY itself afterward.

**7. Uninstall/reversal procedure:** Remove the setgid bit and/or delete
the helper binary; restore prior `input`-group membership if it was
removed (`sudo usermod -aG input $USER`). Both are simple, standard,
fully-reversible file-permission and group operations — no persistent
kernel-level state, no systemd unit files, no polkit policy files are part
of this specific proposal.

**No code implementing this was written.** This section is the requested
decision material only.

Given the STOP above, Step 2.5's concrete deliverable is: (a) the audit and
evaluation in sections 4-7, (b) confirmation that KEEBY's existing device
access is already minimal in every dimension *within* the current
group-based mechanism (read-only, no grab, no write, single device), and

  (see section 15).

continues to be what makes keyboard access work today; this report treats
that as documented, evaluated, and *not silently accepted as the final
answer* — see section 7's proposal for what a narrower production
architecture would look like, pending approval.

## 14. Session/lock behavior

Observed/reasoned per case:

1. **Normal active session**: works today, as verified throughout this
   report.
2. **Session becomes inactive / another user becomes active**: **not
   tested live** (would have required locking or switching the user's
   active session, which this report did not do without being asked to).
   Reasoned from mechanism: since access is via a permanently-open,
   group-permission-granted fd — not a logind/seatd session-scoped ACL —
   there is no `EVIOCREVOKE` delivery path here (that revocation mechanism
   applies to `uaccess`-tagged devices under logind's session management,
   which section 4 established does not cover this device). **KEEBY's
   currently-open fd would not be revoked by a session becoming inactive.**
   This is stated as a reasoned conclusion from the verified mechanism, not
   as an empirically observed result.
3. **Lock screen**: same conclusion and same caveat as case 2 — reasoned,
   not live-tested. Explicitly *not* something this step attempted to
   design around speculatively, per the task's own instruction not to
   build speculative lock-screen integration without observed justification.
4. **Device disconnects**: **tested** (new regression test, section 15) —
   the capture thread observes `-ENODEV`, exits cleanly, and
   `InputCapture::connected()` becomes `false`; `main()` now surfaces this
   once via stderr and keeps running (tray/Ctrl+C quit still work). No
   crash.
5. **Device reconnects / external keyboard appears after startup**: **not
   supported** — no rescan logic exists; this remains a known limitation
   (section 21), explicitly out of scope per the task's instruction not to
   build a complete hot-plug subsystem.

## 15. Bug found and fixed (Steps 2.1-2.4 regression)

**Bug**: `input_capture.cpp`'s permission-denied error message claimed
"rely on your session's logind/seatd seat ACL (uaccess) if your distro's
udev rules grant it dynamically instead of the group" as a valid
alternative fix. **Root cause**: this was written without verifying that
`uaccess` actually applies to keyboard-class devices; it does not (section
4, point 10) — stock systemd's `70-uaccess.rules` only tags joysticks.
**Fix**: rewrote the message to cite only the mechanism verified to
actually work (`input`-group membership), removing the misleading
alternative. **Regression risk**: none — no test asserted on the previous
wording (checked: `grep -rn "permission_denied\|EACCES" tests/` found no
matches). Also added, as a related but separate gap (not strictly a
"regression" since the prior behavior was explicitly documented as
intentional — "no console logging from a background thread's steady-state
path" — but a real functional gap against this step's own error-handling
requirement to distinguish "device disappeared"): `InputCapture::connected()`
and a one-time stderr surfacing in `main()`. Regression test added in
`tests/input_capture_test.cpp` (see section 17).

# Step 2.5B: implementation of the approved privileged-helper architecture

## 24. Final privilege architecture

A new executable, `keeby-inputd`, is the only component in the system that
opens `/dev/input/event*`. It is installed setgid `root:input`, mode
`2750` (`-rwxr-s---`), owned by `root:input`, **not** setuid-root and
**not** granted any Linux capability. `keeby` itself (the main process)
never requests elevated privilege at any point and never becomes a member
of `input` by virtue of running the helper — it talks to the helper only
over a private, unnamed `AF_UNIX SOCK_SEQPACKET` socket pair it creates
itself via `socketpair()` before forking.

Sequence: `keeby` (unprivileged, UID 1000) creates the socket pair, forks,
the child `dup2()`s its end onto fd 3, `execv()`s `keeby-inputd`. The
kernel grants `keeby-inputd` the `input` supplementary/effective GID at
`exec()` time because of the setgid bit on the file — this is the *only*
place privilege enters the picture, and it is scoped to that one process,
not to the invoking user's login session.

**Corrected in Step 2.5C**: mode `2750` alone only establishes *where the
setgid privilege comes from*; it does not by itself determine *who may
execute the helper*, which is the actual security boundary — anyone who
can execute `keeby-inputd` receives keystrokes through its socket (section
40). Without an ACL, execute permission on a `root:input` mode-`2750` file
tracks `input`-group membership exactly, which is the property Step 2.5B
removed the interactive user from (section 32) — so mode 2750 alone left
no non-root account able to execute the helper at all once that happened
(section 39). Part 3 (sections 39-45) covers the fix: a POSIX ACL granting
execute to the one desktop account.

## 26. Helper startup sequence

1. `keeby-inputd` validates `fd 3`: must be a valid, open, `AF_UNIX`,
   `SOCK_SEQPACKET` socket (checked via `getsockopt` with `SO_TYPE` ==
   `SOCK_SEQPACKET` and `getsockopt` with `SO_DOMAIN` == `AF_UNIX`).
   Anything else → exits nonzero immediately, before any device is touched.
2. Resolves a target device path: either the single argument passed by the
   parent, or (if empty/absent) a scan of `/dev/input/event0..31` for a
   device exposing the same "looks like a full keyboard" capability set
   `InputCapture` used to check itself (`KEY_A`, `KEY_Z`, `KEY_SPACE`,
   `KEY_ENTER`).
3. Opens that device `O_RDONLY | O_NONBLOCK | O_CLOEXEC | O_NOFOLLOW`,
   `fstat`s the resulting fd to confirm `S_ISCHR`, and only then runs
   `libevdev_new_from_fd` + the same 4-key capability check against the
   **opened fd**, not the pathname (see section 28 — this is the TOCTOU
   defense).
4. Calls `drop_privilege_or_die()` (section 27) — this is the **last**
   thing that happens before any data can flow to the parent.
5. Sends one `wire::Message{type = Ready}` to the parent over fd 3.
6. Enters a `poll()` + `libevdev_next_event()` loop, forwarding one
   `wire::Message{type = KeyEvent, ...}` per keyboard event; exits (closing
   its end of the socket) on `-ENODEV` (device unplugged) or any
   unrecoverable evdev error.

The parent (`InputCapture::start()`) blocks on `poll()`+`recv()` for the
`Ready` message (5000 ms bounded timeout) before returning success; any
failure at any of steps 1-5 above is observed by the parent as either a
nonzero exit (reaped via `waitpid`) or a socket close with no `Ready`
message, and is treated identically — `start()` fails, any partially
started state (audio side, in `EngineController`) is rolled back, and the
child is terminated/reaped if it is still around.

## 27. Permanent privilege-drop mechanism

```cpp
const gid_t real_gid = getgid();               // the invoking user's real GID (1000)
setresgid(real_gid, real_gid, real_gid);        // drop primary/effective/saved GID to it
// verify via getresgid(): all three must now equal real_gid, else die
// verify 'input' GID is not present in real/effective/saved, else die
setgroups(1, &real_gid);                        // best-effort: clear supplementary groups
prctl(PR_SET_NO_NEW_PRIVS, 1, 0, 0, 0);
prctl(PR_SET_DUMPABLE, 0);
```

`setresgid()` reliably drops the **primary** group identity the setgid bit
granted at `exec()` time, and this is verified, not assumed — the code
calls `getresgid()` immediately after and refuses to continue (`die_msg`,
process exit) if the drop cannot be confirmed, or if the `input` GID is
still present in real/effective/saved after the call.

**The one nuance that matters and is disclosed rather than hidden**:
`setresgid()` does **not** touch **supplementary groups**, a separate
credential axis from primary GID. Supplementary groups are inherited
unchanged across `exec()` of a setgid (non-setuid) binary, and clearing
them via `setgroups()` requires `CAP_SETGID` — which a plain setgid
process does not have (only the file's setgid *bit* granted the primary
GID at exec; it grants no capability). So `keeby-inputd` **attempts**
`setgroups(1, &real_gid)` anyway, and:
- if it succeeds (e.g. some future deployment where the binary does hold
  `CAP_SETGID`), supplementary groups are now also clean;
- if it fails with `EPERM` (the expected case, confirmed live — see
  section 32), the failure is treated as non-fatal and reported to stderr;
  any other errno is treated as fatal.
- separately, the code checks whether `input`'s GID is still present in
  the process's *supplementary* group list after this and, if so, prints
  an explicit stderr note that this is inherited from the invoking
  session, not granted by the binary itself.

Practical meaning: if the interactive user's account is a member of
`input` (the pre-existing state this whole step exists to move away from),
the helper's supplementary groups still carry that membership after the
drop, because the kernel gave the *process* that supplementary group when
it inherited it from the parent shell — independent of the setgid bit.
This is not a flaw in the drop logic; it is a structural fact about
`setresgid()`/`setgroups()`/`CAP_SETGID` that no correctly-written
non-root setgid binary can fully work around on its own. **The only way to
close this residual gap is for the interactive user's account to leave the
`input` group and start a fresh login session**, at which point there is
nothing left for the helper to inherit. See section 32.

## 28. Device validation rules (TOCTOU avoidance)

The device path is validated twice, deliberately at different layers:
- **Before open**: `is_valid_event_path()` checks the string matches
  `/dev/input/eventN` (fixed prefix, all-digit suffix) — rejects path
  traversal/symlink-name tricks before any syscall touches the
  filesystem.
- **After open**: the security-relevant checks (character device via
  `fstat`, and "is a keyboard" via `libevdev`+capability bits) are run
  against the **already-open file descriptor**, not re-derived from the
  path string. This is the standard defense against a device node being
  replaced between a path-based check and the actual open — by the time
  the checks run, the fd already refers to whatever the kernel resolved
  at `open()` time, and `O_NOFOLLOW` additionally refuses to open through
  a symlink at all.

Exactly one device is opened per helper process lifetime; there is no
retry-a-different-device path and no re-open call anywhere in
`inputd_main.cpp` after the initial discovery/open.

## 29. IPC protocol / wire format

`src/input_wire.hpp` defines a fixed-size, versioned-by-size message:

```cpp
enum class MessageType : uint8_t { Ready = 0, KeyEvent = 1 };
struct Message {
    uint8_t  type;
    uint8_t  kind;      // KeyEvent only: 0=up, 1=down, 2=repeat
    uint16_t code;       // KeyEvent only: evdev key code
    uint32_t reserved;   // padding/future use, always zero-initialized
    uint64_t ts_ns;
};
static_assert(sizeof(Message) == 16);
```

`SOCK_SEQPACKET` preserves message boundaries (no manual framing needed);
every `send()`/`recv()` on this socket moves exactly one `Message`. The
parent's read side rejects (silently drops, does not crash) anything that
doesn't decode as exactly 16 bytes with `type ∈ {Ready, KeyEvent}` and
`kind ≤ 2`. The socket is created directly by `keeby` via `socketpair()`
— never a named/pathname socket, never visible in the filesystem, never
reachable by any other process on the system.

## 30. Process lifecycle behavior

- **Startup**: `fork()` + `execv()` from the parent; `SIGCHLD` handling is
  the default (reaping is explicit, via `waitpid`, not signal-driven).
- **Normal shutdown**: parent calls `terminate_and_reap()` — sends
  `SIGTERM`, polls `waitpid(..., WNOHANG)` for up to ~1s, escalates to
  `SIGKILL` if still alive, and always calls a final blocking `waitpid` so
  no zombie is ever left behind. Verified bounded (<2s) in
  `input_capture_test`.
- **Helper dies unexpectedly** (crash, device unplug → helper exits on
  `-ENODEV`): the parent's forwarding thread observes EOF/error on
  `recv()`, sets `connected_ = false`, and the thread exits; `stop()`/the
  destructor still reaps the now-dead child via `waitpid` without
  blocking indefinitely.
- **Startup failure** (bad helper path, helper exits before sending
  `Ready`, helper hangs): bounded by the 5000 ms `Ready`-wait timeout in
  the parent; `start()` returns an error and rolls back any partially
  started state. No `system()`/`popen()`/shell involved anywhere in the
  spawn path — only `socketpair`/`fork`/`dup2`/`execv`.

## 33. Negative security test

`keeby-inputd` installs a `SIGUSR1` handler that, on receipt, attempts to
open a **different** `/dev/input/eventN` than the one it already holds,
and reports success/failure to stderr — a runtime, self-administered proof
of whether the privilege drop actually restricts further device access.

**Corrected in Step 2.5C**: this section originally claimed the handler
was "async-signal-safe: only `write()`/`open()`/`close()`, precomputed
message buffers." That was false as written — the probe path was built
with `std::snprintf()` *inside* the signal handler itself, and `snprintf`
is not on the async-signal-safe list (POSIX `signal-safety(7)`). Fixed in
Step 2.5C (section 42): the probe path is now computed once in `main()`,
before `sigaction(SIGUSR1, ...)` is armed, and the handler calls only
`open()`/`close()`/`write()` against that precomputed buffer — the
async-signal-safety claim is accurate as of that fix, not before it.

Result, sent to the Stage 2 (real setgid) helper: **the probe reported
`"keeby-inputd: SECURITY TEST FAILURE: post-drop open() unexpectedly
succeeded"`.**

This is the expected, honestly-disclosed outcome given the state described
in sections 27 and 32 — the *primary* GID drop is real and verified, but
the interactive user's account is still ambiently an `input`-group member
via *supplementary* groups, which the helper cannot strip on its own. The

still exists and refusing to let the report claim otherwise. It is not a

## 36. Before/After threat model

**Before (status quo at the start of Step 2.5, section 3-6)**: any process
the interactive user's account ever runs — not just KEEBY, not just
during KEEBY's runtime — could read every `/dev/input/event*` node on the
system, for as long as that account remained an `input`-group member
(indefinitely, until manually revoked).

**After (Step 2.5B, as implemented and currently installed)**: exactly one
short-lived, single-purpose, non-setuid process (`keeby-inputd`) — spawned
only while `keeby` is running, exiting when `keeby` exits — holds a raw
read handle to exactly one validated keyboard device, for the duration of
that one `keeby` session. Every other process the same account runs,
including `keeby` itself, has no direct device access and no `input`
credential of its own. This is a real, verified reduction in blast radius
compared to Before: `keeby-inputd`'s own attack surface is a small,
audited, single-file binary with no dynamic dependencies beyond
`libevdev`, versus the previous state where *anything* run by that
account had the access.

**Corrected in Step 2.5C**: "has no direct device access and no `input`
credential of its own" is true but incomplete as a security claim — it
describes device *credentials* only. As installed at this point (mode
2750, no ACL), any of those same processes could simply execute
`keeby-inputd` directly and receive keystrokes through its own socket,
because the helper accepts fd 3 from whatever process forked/exec'd it and
never authenticates who that is (section 40). No device credential is
needed to do this — only permission to execute the helper file, which is a
separate axis this section did not account for. See section 43 for the
corrected Before/After model.

keylogger prevention, and it does not yet claim the interactive account is

1. The interactive user's account is still, today, a member of `input`

2. Even once that is resolved, a malicious process running as the same
   UID as `keeby` could still, in principle, `ptrace()` or otherwise
   interfere with `keeby` itself, or read the private socket's traffic if
   it could attach to the process — this step narrows *device* access, it
   does not sandbox `keeby` as a whole, and no such sandboxing was in
   scope for this step.

## 40. The security principle

`keeby-inputd` does not authenticate whoever is on the other end of fd 3 —
it only checks that fd 3 is a valid `AF_UNIX SOCK_SEQPACKET` socket
(section 26, step 1). Fd 3 exists because whatever process executed the
helper created the socket pair itself, via `socketpair()`, before
forking — exactly what `InputCapture::start()` does. Any program able to
execute `keeby-inputd` can reproduce that same handshake in a few lines
and receive every keystroke the helper forwards. That is how KEEBY's
architecture works by design (it is also why Keeby on macOS requires
"Input Monitoring" permission — the same underlying capability, gated a
different way). **So who may execute the helper is the actual security
boundary** — not the setgid bit and not device permissions, which only
control where the privilege to *open the device* comes from, not who can
*receive events from the process that holds it*. A world-executable
(`2755`) helper would let any local account, or any compromised system
service running under a different account, execute it and read the user's
keystrokes — strictly worse than the pre-existing `input`-group model for
cross-account safety, which at least required group membership rather
than merely a local shell.

## 41. The decision and alternatives considered

The user's decision, exact wording: **"Only my user, via ACL."** Keep the
binary `root:input`, mode `2750`, and grant execute to the one desktop
account with a POSIX ACL:
```
setfacl -m u:<user>:x /usr/local/bin/keeby-inputd
```
Root and members of `input` (currently only `brltty`, which already has
direct device access and gains nothing new from this) can also execute it;
nobody else can.

Alternatives considered and rejected:
- **ACL plus an active-seat check** (verify the caller is on the active
  logind seat before the helper forwards events): real defense-in-depth,
  rejected as unrequested complexity for a single-user desktop machine —
  it would add a new runtime dependency (logind/`loginctl` or D-Bus) and
  new multi-seat/remote-session edge cases the ACL alone does not need to
  handle to satisfy this machine's threat model.
- **World-executable (`2755`)**: rejected — this is exactly the boundary
  section 40 identifies as the real risk; it would let any local account
  or compromised system service execute the helper and receive keystrokes.
- **Re-adding the user to `input`**: rejected — this would reintroduce the
  permanent, every-process-this-account-runs credential that Step 2.5/2.5B
  exists to remove, silently regressing the entire privilege-separation
  effort just to fix a permission error.

Merged; Release ctest 7/7 and ASAN/UBSAN 7/7 at the time, reviewed by the

## 43. Updated Before/After threat model (supersedes section 36)

**Before (status quo at the start of Step 2.5)**: any process the
interactive user's account ever ran could read every `/dev/input/event*`
node on the system, indefinitely, via permanent `input`-group membership.

**After Step 2.5B alone (mode 2750, no ACL — now known to be incomplete)**:
device *credentials* were narrowed to one process, but execute permission
on the helper still silently tracked `input`-group membership — so the set
of accounts able to receive keystrokes through the helper's socket was
never actually decoupled from `input`-group membership the way section 36
implied. Once the user correctly left `input` (Step 2.5B's own stated
goal), the helper became unexecutable by anyone but root (section 39).

**After Step 2.5C (current, pending the setfacl step in section 44)**:
execute permission on `/usr/local/bin/keeby-inputd` — the actual boundary
identified in section 40 — is granted to exactly: root, members of `input`
(only `brltty`), and the one named desktop account via POSIX ACL. No other
local account or service can execute the helper, and the interactive
account no longer needs `input`-group membership to do so.

**What this still does not claim** (unchanged in kind from section 36,
restated precisely): this is not complete keylogger prevention, and it
never claimed to be. Residual risks, disclosed rather than minimized:
1. Any process running as the *same UID* as the granted desktop account
   can still execute `keeby-inputd` directly and receive keystrokes
   through its own socket pair — the ACL grants the account execute
   permission, and every process that account runs inherits that same
   permission. This is inherent to how a global keyboard-sound application
   works on Wayland (there is no per-application input-event ACL in the
   kernel or in Wayland itself); it is also why Keeby on macOS requires an
   explicit, user-visible "Input Monitoring" grant rather than claiming to
   prevent this class of access entirely.
2. A process running as that same UID could still, in principle,
   `ptrace()` `keeby` itself, or attach to it to read the private socket's
   traffic — this step (like 2.5B) narrows *device* access and *helper
   execute* access; it does not sandbox `keeby` as a whole, and no such
   sandboxing is in scope here.
3. Root, and any process running as root, can always execute the helper —
   unavoidable under the standard Linux permission model and not treated
   as a residual risk worth mitigating on a single-user desktop machine.

## 46. Pointer motion for the visualizer (user-approved scope change)

Wayland gives an application no API to query the global cursor position, so
the on-screen keyboard overlay (docs/013-visualizer.md) cannot simply ask
"where is the mouse". The user was offered the alternatives and explicitly
chose: **"Estimate the cursor from mouse movement"** — i.e., widen
`keeby-inputd` from "one keyboard" to "one keyboard plus pointer devices",
forwarding relative motion samples the unprivileged parent turns into a
drifting position estimate, on the understanding that the estimate may
drift from the real cursor over time (no absolute position is ever known or
forwarded — see below).

**What is opened.** In addition to the one keyboard device (unchanged),
`keeby-inputd` now also opens up to 4 pointer devices, auto-discovered the
same way the keyboard is (`/dev/input/event0`..`31`), with the same flags:
`O_RDONLY | O_NONBLOCK | O_CLOEXEC | O_NOFOLLOW`. All of this happens
strictly BEFORE `drop_privilege_or_die()` — the privilege-drop call itself,
its post-drop verification (re-reading real/effective/saved gid), and the
SIGUSR1 negative probe are byte-for-byte unchanged from section 27/33. A
pointer device that is absent, unplugged, or later disappears is never
fatal: the keyboard remains the one device whose loss ends the session (see
`inputd_main.cpp`'s main loop), exactly as before this change.

**How each candidate is validated.** Same TOCTOU-safe shape as the keyboard
(section 28): the opened fd, not the path string, is the source of truth.
`libevdev_new_from_fd()` on the actual fd, then a pure classification
(`src/pointer_input.hpp::classify()`, unit-tested directly with no fd or
device involved) decides which of exactly two shapes qualifies:

- **Mouse**: `EV_REL` with both `REL_X` and `REL_Y`.
- **Touchpad**: (`ABS_X`+`ABS_Y`, or `ABS_MT_POSITION_X`+`ABS_MT_POSITION_Y`)
  AND `BTN_TOOL_FINGER` AND `INPUT_PROP_POINTER`.

Anything else is rejected and the fd is closed immediately — in particular
this excludes absolute drawing tablets (no `BTN_TOOL_FINGER`, or no
`INPUT_PROP_POINTER`) and touchscreens (`INPUT_PROP_DIRECT`, not
`INPUT_PROP_POINTER`), and it never matches a keyboard (no relative or
absolute pointer axes at all). No `EVIOCGRAB` and no writes on any pointer
device, mirroring the keyboard's passive-observer contract exactly.

**What is forwarded, and what never is.** Per `SYN_REPORT`, at most one
summed `(dx, dy)` sample per device travels over the existing
`keeby-inputd` <-> `InputCapture` socket as `wire::MessageType::PointerMotion`
(`src/input_wire.hpp`):

- **Mouse**: raw `REL_X`/`REL_Y` counts summed since the last `SYN_REPORT`.
- **Touchpad**: the one-finger position delta only — a
  `TouchpadFingerTracker` state machine (pure, unit-tested,
  `src/pointer_input.hpp`) requires exactly one finger down for both this
  sample and the previous one; 2+ fingers (scrolling), a lift/replace, or
  the very first sample after either resets the baseline and forwards
  nothing, so a gesture or a finger swap never produces a spurious jump.
  The delta is converted from device units to "mouse-equivalent" units
  (`mm * 1000/25.4`, using the device's own `ABS` resolution, or a fixed
  fallback constant if it reports 0) so a touchpad drag lands in the same
  numeric scale a physical mouse's raw counts already do.

Both components are clamped to `[-32767, 32767]` and packed into the
existing 16-byte `wire::Message`'s `reserved` field (`pack_motion()`/
`unpack_motion()`, unit-tested for exact round trip) — no wire format
change beyond one new `MessageType` discriminant. **Never forwarded, on
either device class**: button state, scroll wheel data, absolute
position/coordinates, multi-finger gesture data, or anything from a
rejected (tablet/touchscreen/keyboard) device.

**Where it goes, and where it never goes.** `InputCapture`'s existing
forwarding thread (already off the RT path — see section 34/section on
real-time safety) decodes `PointerMotion` the same way it decodes
`KeyEvent`, but routes it exclusively to a second, separate tap
(`set_visualizer_motion_transport`) — never into the primary
`KeyEventTransport` that feeds `AudioBoundary`. `EngineController` wires
that tap only when the visualizer is both enabled AND its position is
`follow-cursor`; any other position (or the visualizer disabled) leaves the
tap unwired, so the forwarding thread decodes the sample and drops it,
never queuing it anywhere. From there `VisualizerService`'s existing
sender thread (docs/013-visualizer.md) coalesces pending motion into at
most one `VizMessage` per loop iteration and forwards it to
`keeby-visualizer` over the same private, unnamed `SOCK_SEQPACKET` socket
key events already use — never D-Bus, never a named/pathname socket, never
written to any log or file, exactly like keystroke data.

**Residual risk.** Mouse/touchpad motion is lower-sensitivity than
keystroke content (no character or password is recoverable from summed
relative deltas), but it is still real input data leaving a privileged
process, and the same same-UID caveat from section 40 applies unchanged:
any other process running as this user can already read the same
`/dev/input/eventN` nodes' raw content once it has `input`-group access, or
observe window activity through the compositor. This change does not widen
that boundary — it adds a second passive-observer data path through the
same already-audited privilege-separated helper, subject to the same
group/ACL controls (sections 27, 41-42) as the keyboard path it was
modeled on.

**Privilege-drop order.** Unchanged and load-bearing: ALL device opens
(keyboard, then up to 4 pointers) happen first, then
`drop_privilege_or_die()` runs exactly once, then its verification, then
`PR_SET_NO_NEW_PRIVS`/`PR_SET_DUMPABLE`, then the SIGUSR1 handler is armed,
then the one-time `Ready` message is sent. No device is ever opened after
the drop; a pointer device that appears later (hotplugged mid-session) is
never picked up by this process — only what was open at startup is ever
read from, identical to the keyboard's existing single-discovery-at-startup
behavior.

## 47. Exact pointer tracking via libinput (user-approved, 2026-09-26)

Section 46's raw REL/ABS forwarding made the overlay *estimate* the cursor
from a hand-rolled gain curve; in practice this drifted from niri's real
cursor by roughly 3.4x, because niri moves its own pointer by whatever
libinput's accelerated `dx`/`dy` already is (niri `src/input/mod.rs:2405`,
`new_pos = pos + event.delta()`; smithay maps `delta()` straight to
`libinput_event_pointer_get_dx/dy()`), not by the raw device counts
`keeby-inputd` was forwarding. The user was offered three options —
**"Exact tracking (Recommended)"**, "Snap on typing start" (no helper
change; a zero-length virtual-pointer nudge plus a probe at the first
keypress after motion, with the cursor briefly reappearing under
`hide-when-typing`), and "Gain fix only" — and chose exact tracking:
`keeby-inputd` runs its own libinput path-backend context over the same
pointer devices it already
opens, so it forwards libinput's own accelerated deltas instead of
recomputing an approximation of them. This section supersedes section 46's
*mechanism*; section 46's scope decision (why pointer devices are opened at
all, and the residual-risk analysis) still stands unchanged.

**Scope unchanged.** The set of devices opened, and the gate that decides
whether a candidate is accepted, are byte-for-byte what section 46
describes: up to 4 pointer devices, `/dev/input/event0`..`31`,
`O_RDONLY | O_NONBLOCK | O_CLOEXEC | O_NOFOLLOW`, `classify()`'s
mouse/touchpad shape check, `EVIOCSCLOCKID`, all of it strictly before
`drop_privilege_or_die()`. The keyboard path is untouched byte-for-byte.
What changed is what happens to those already-opened, already-validated
fds *after* the drop.

**What's new, and where it runs.** Post-drop, `keeby-inputd` creates a
libinput path-backend context (`libinput_path_create_context()`) and adds
each pointer fd to it (`libinput_path_add_device()`), so libinput's own
motion/acceleration computation replaces the hand-rolled REL-summing and
`TouchpadFingerTracker` state machine section 46 described (both now
deleted, along with `units_to_mouse_equivalent()` — see
`src/pointer_input.hpp`/`src/inputd_main.cpp`). This pulls in real
filesystem/library access that did not exist before, all of it **strictly
post-drop, over already-open read-only fds**:

- **libinput itself is `dlopen()`'d at runtime, never linked at the ELF
  level — this is load-bearing, not an implementation detail.** An earlier
  version of this change linked `libinput` directly
  (`target_link_libraries(keeby-inputd PkgConfig::LIBINPUT)`), which made
  `ldd keeby-inputd` list `libinput.so` **and its full transitive
  dependency chain**: `libwacom`, `libgudev` (hence `libglib-2.0` and
  `libgobject-2.0`), `liblua5.4`, `libpcre2-8`, `libffi`, `mtdev`,
  `libudev`. Every one of those becomes an ELF `NEEDED` entry, so the
  dynamic linker maps and runs **all of their ELF constructors
  (`.init_array`, e.g. GLib's own initialization, which reads
  `G_DEBUG`/`G_MESSAGES_DEBUG` and similar environment variables) before
  `main()` — i.e. before `drop_privilege_or_die()` — inside a process that
  is still setgid-`input` at that point.** GLib's own documentation
  explicitly states it does not support being used in a setuid/setgid
  program. That is a real widening of what runs privileged, independent of
  anything this code's own logic does, and was caught in review before
  merge. The fix: `CMakeLists.txt`'s `pkg_check_modules(LIBINPUT REQUIRED
  libinput)` now supplies **include directories only** (`${LIBINPUT_INCLUDE_
  DIRS}`, no `IMPORTED_TARGET`, never passed to `target_link_libraries()`),
  and `src/libinput_loader.hpp` `dlopen("libinput.so.10", RTLD_NOW |
  RTLD_LOCAL)`s the real library and `dlsym()`s every function
  `inputd_main.cpp` calls into a `LibinputApi` struct of typed function
  pointers — called from `setup_libinput()`, strictly after
  `drop_privilege_or_die()`, exactly like context creation itself. If
  either the library or any single symbol fails to resolve, it logs one
  line and falls back to keyboard-only, the same as when no pointer device
  exists. **Verified**: `ldd build/integ-rel/keeby-inputd` lists only
  `libevdev`, `libc`, `libstdc++`, `libgcc_s`, `libm`, `ld-linux` — none of
  libinput, libwacom, libgudev, glib, gobject, lua, pcre2, ffi, mtdev, or
  libudev (see the step report for the before/after `ldd` output). A bare
  soname (`"libinput.so.10"`, never a path) is used deliberately: the
  kernel sets `AT_SECURE` for this process's entire lifetime because the
  binary is exec'd setgid, and glibc's dynamic linker keeps honoring
  secure-execution mode (ignoring `LD_LIBRARY_PATH`/`LD_PRELOAD`, searching
  only trusted system library directories) for every `dlopen()` this
  process makes afterward, not just its original exec-time linking — so
  this run-time load cannot be redirected by environment even though it
  happens after this process voluntarily dropped its own group privilege.
  `libinput_loader.hpp` never calls `dlclose()` once loading fully
  succeeds (the process is short-lived and single-purpose, so there is no
  reason to reload, and this sidesteps any question of whether something
  is still using it); `tests/libinput_loader_test.cpp` resolves every
  symbol against the real installed `libinput.so` and exercises
  `path_create_context()`/`unref()` end-to-end, so a symbol-name typo
  fails on any machine that builds this project, not only on the user's.
- libinput's path backend reads the target device's `st_rdev` via `stat()`
  on the path string, then asks libudev (`udev_device_new_from_devnum()`)
  for the matching device object — reads against `/sys` and
  `/run/udev/data`, both world-readable (libinput 1.32
  `src/path-seat.c:326-354`).
- libinput matches the device against its own quirks database under
  `/usr/share/libinput/*.quirks` (also world-readable, confirmed
  `root:root 644` on this machine) to pick per-device behavior tweaks
  (button numbering, trackpoint ranges, etc.). Reading the libinput 1.32
  source further: this quirks lookup also honors the `LIBINPUT_QUIRKS_DIR`
  environment variable in place of the compiled-in data path
  (`libinput_init_quirks()`, `src/libinput.c:1911`), and additionally
  parses `$XDG_RUNTIME_DIR/libinput/` (falling back to
  `/run/user/<uid>/libinput/` if unset) as a second, always-checked quirks
  location (`quirks_init_subsystem()`, `src/quirks.c:1275`). Neither is a
  privilege gain: both are read post-drop, both are user-level paths this
  unprivileged process already has full read/write access to regardless
  (its own environment, and its own runtime directory), and niri itself
  parses that identical `$XDG_RUNTIME_DIR/libinput/` location via the same
  libinput version for the exact same reason. Worst case, whatever the
  user (or something else running as the user) can already put there
  changes touchpad/mouse *behavior* tuning — never a privilege boundary,
  since this process's own group privilege is already gone by the time any
  of this runs.
- **No new device is ever opened.** libinput's `libinput_interface.
  open_restricted(path, flags, user_data)` callback
  (`pointer_open_restricted()` in `inputd_main.cpp`) never calls `open()`:
  it looks up which pre-drop-opened fd's path string matches exactly, and
  returns `fcntl(that_fd, F_DUPFD_CLOEXEC, 0)` — a dup of a read-only fd
  this process already held before the drop — or `-EACCES` if nothing
  matches. `close_restricted()` only closes that dup. libinput requests
  `O_RDWR | O_NONBLOCK | O_CLOEXEC` (libinput 1.32 `src/evdev.c:2339`,
  `:2965`), but the requested flags are irrelevant: what comes back is
  always the read-only dup regardless, and libinput has no way to open
  anything itself once this hook is the only path to an fd.
- **Confirmed a read-only fd is sufficient** by reading the libinput 1.32.0
  source (matches this machine's installed `libinput 1.32.0-1.1`): the
  *only* two `write()` calls anywhere in libinput's evdev code are (a)
  `evdev_device_led_update()` (`src/evdev.c:369`), gated by
  `if (!(device->seat_caps & EVDEV_DEVICE_KEYBOARD)) return;` before
  touching the fd, and never invoked at all unless the caller calls
  `libinput_device_led_update()` (this code never does); and (b)
  `fallback_lid_keyboard_event()`'s `SW_LID` resync
  (`src/evdev-fallback.c:750`), reachable only through an internal-keyboard
  lid-switch listener that is never wired for a plain mouse/touchpad.
  Since this context only ever adds mouse/touchpad-classified devices and
  never a keyboard, neither path is reachable. There is no `EVIOCGRAB` and
  no other write-requiring ioctl (`EVIOCSFF`, `EVIOCRMFF`, `EVIOCSKEYCODE`,
  `EVIOCSABS`) anywhere in libinput's source. `evdev_device_create()`'s own
  syspath check (`evdev_device_have_same_syspath()`, `src/evdev.c:2117`)
  is a plain `fstat()`. And `EVIOCSCLOCKID` (which libinput also applies at
  add time, `src/evdev.c:2364`) is the same ioctl this process's own
  pre-drop code already applies successfully to a read-only fd today, and
  since `fcntl(F_DUPFD_CLOEXEC)` shares the same underlying open file
  description as the fd it dups (POSIX: dup-family calls share file status
  and any driver-side per-open state, unlike a second independent `open()`
  of the same path), libinput's own call is a same-value no-op against
  state this process already set.
- **No keyboard is ever added** to this context, and this code never calls
  `libinput_suspend()`/`libinput_resume()` or any plugin-registration API.
  Log priority is forced to `LIBINPUT_LOG_PRIORITY_ERROR`
  (`libinput_log_set_priority()`) — this is in fact already libinput's own
  documented default, set explicitly here as a stated contract rather than
  an assumed one. No key or motion data is ever logged, only a single
  startup line with a device *count* (see `setup_libinput()`).
- **Disclosed finding, not a design choice:** calling the documented
  `libinput_path_add_device()` API (the one this section uses, and the
  only supported way to add a path-backend device) internally triggers
  `libinput_plugin_system_autoload()` (`src/path-seat.c:386`) —
  unconditionally, as part of that public API's own implementation, not
  because this code calls anything plugin-prefixed itself. This machine's
  `libinput 1.32.0-1.1` package is built with Lua plugin support
  (`depends: lua54`, confirmed via `ldd` against the installed
  `libinput.so`), so on first `add_device()` autoload would scan
  `/etc/libinput/plugins` and `/usr/lib/libinput/plugins` for `*.lua`
  files and load+execute any found, in addition to always loading
  libinput's own built-in internal plugins (button-debounce,
  mouse-wheel/low-res splitting, mtdev — compiled into `libinput.so`
  itself already, not a new file-based surface). Both directories are
  confirmed empty/nonexistent on this machine today, so nothing external
  loads. This is an unavoidable property of linking libinput 1.32 with Lua
  support at all — niri's own compositor-side libinput usage (smithay's
  udev backend) hits the exact same `libinput_plugin_system_autoload()`
  code path already, so this is not a new attack surface keeby introduces,
  only one worth stating plainly rather than silently discovering later.
  This code deliberately does not call `libinput_plugin_system_append_
  path()`/`append_default_paths()` itself to suppress this, since doing so
  would itself be exactly the "libinput plugin-system API call" this
  section is scoped to avoid making.

**What's forwarded, and what never is.** Unchanged from section 46's
contract: only motion, never buttons, scroll, absolute position, or
gesture data, and only for the mouse/touchpad-classified devices opened
pre-drop. Concretely, only `LIBINPUT_EVENT_POINTER_MOTION` events are ever
inspected (`libinput_event_get_type()` filters everything else, including
`LIBINPUT_EVENT_POINTER_MOTION_ABSOLUTE`, button, scroll, gesture, and
device add/remove events, which are still drained via
`libinput_event_destroy()` but otherwise ignored). Each such event's
already-accelerated `libinput_event_pointer_get_dx()`/`get_dy()` is folded
through `pointer_input.hpp::carry_and_truncate()` (a per-device, per-axis
carried remainder — sub-pixel deltas at low speed are common and must not
be silently rounded away every time) and sent as exactly one
`wire::PointerMotion` message per libinput event when the truncated
integer delta is non-zero on either axis — no summing across events, no
change to the wire format itself (`src/input_wire.hpp` is untouched).

**Acceleration settings mirror the user's own niri config exactly**
(`ponytail` comment at `apply_niri_pointer_settings()` in
`inputd_main.cpp`, niri `src/input/mod.rs:4674-4962`
`apply_libinput_settings()`): mouse gets `accel-profile "flat"` and speed
0; touchpad gets speed 0, tap-to-click enabled with
`tap-button-map "left-right-middle"`, `dwt`/`dwtp` disabled, drag-lock
disabled, and both touchpad accel-profile and tap-and-drag left at
device default — because that is what this user's niri config actually
sets, nothing more. This is hardcoded, not read from niri's config file;
the upgrade path if this ever needs to serve a different config is to pass
settings from `keeby` via `argv` instead of mirroring a constant here.

## 48. Mouse button audio events (user-approved scope extension, 2026-10-01)

The motion-only boundary recorded in sections 46 and 47 was the boundary at
the time of those changes. On 2026-10-01, the user explicitly approved
left-, right-, and middle-button press/release events from pointer devices
that `keeby-inputd` already opens. This section records the limited later
extension; it does not rewrite the historical decision above.

The implementation uses the same pre-drop discovery, read-only file
descriptors, post-drop libinput context, and private unnamed
`SOCK_SEQPACKET` helper socket already used for pointer motion. It adds no
device open, device class, write, grab, privilege, D-Bus method, or log
field. For each `LIBINPUT_EVENT_POINTER_BUTTON`, only `BTN_LEFT` (272),
`BTN_RIGHT` (273), and `BTN_MIDDLE` (274) in pressed or released state are
forwarded as the existing `wire::MessageType::KeyEvent`. `InputCapture`
places them on the existing audio event transport; the mixer maps them to
the selected profile's press/release slots. Events are forwarded
individually, not combined with pointer-motion samples. The visualizer tap
continues to receive only codes below 256, so button codes and `KEY_FN`
(464) do not enter its keyboard layout.

This applies to button events emitted by the existing mouse and touchpad
pointer devices; it does not promise that every physical click or touch
produces a libinput button event. Pointer motion keeps its earlier path.
Scroll, absolute coordinates, gestures, and every other button code remain
ignored. Button capture and forwarding occur in the post-drop helper and
input thread. The PipeWire real-time callback consumes the bounded event
queue and mixes the selected samples, including button press/release
triggers.

The user approval and automated coverage do not establish live hardware
capture, installed-package security, or audible playback. Those checks
remain open in HANDOFF.md and report 018.
