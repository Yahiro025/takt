# 003 — Keeby playback path and imported-source fidelity

Date: 2026-10-01
Status: source, local-pack, and mapping/render audits passed; package 0.1.0-12 automated checks passed; audible result and Mac-app output remain unverified

## Finding

An independent audit matched all **1,114/1,114** copied audio files in 26 local pack directories to pinned source hashes (1,113 WAV files and the Brown OGG). This proves copy integrity; it does not mean every copied file is selected or played. The evidence points to a playback-processing mismatch as a credible cause of the weak and uneven output: the current website browser path raises each decoded WAV separately from its short-window RMS, while the Linux playback baseline shipped in installed package `0.1.0-11` scaled the whole bank from its single largest peak and generated two pitch variants for every source. The measured examples below show why a quiet file can remain quiet in Linux even when another file in its pack has a near-full-scale peak.

This confirms a code-path difference; it does not prove what the user hears or that this fully explains the reported sound. The Mac app binary shows a separate native playback pipeline, but its numeric processing values and output could not be verified from the available static evidence. No sound was auditioned during this investigation.

## Verified website browser playback path

The findings in this section describe the website's browser event path in the captured JavaScript bundle. They do not establish how the Mac app plays the same files.

For ordinary website WAV playback, `Vi` calls `decodeAudioData` and then `B7`. `B7` measures the largest sliding 10 ms RMS window across all channels. It scales that one WAV toward RMS `0.32`, clamps the gain to `[0.55, 16]`, leaves a buffer unchanged when that RMS is at or below `0.001`, and skips scaling when the proposed gain is within `0.005` of `1`. This is per decoded buffer, not per profile bank. All 198 profile WAV files examined here are mono PCM at 44.1 kHz. The audit's gain estimates are calculated from the stored PCM samples; the live browser may decode into its audio context's rate, so the table is a source-level measurement of the algorithm, not a captured gain trace from a running browser.

The page's profile factor `c1` is then used by `hi`: down gain is `min(2.2, 0.28 × c1)` and up gain is `min(2.2, 0.16 × c1)`. The current factors are `0.88` for most website profiles, `0.97` for Akko CS Jelly Black, `1.30` for Akko Piano Pro, `1.47` for Lofree Flow 2 Surfer, `2.02` for Flow 2 Void, and `1.34` for Flow 2 Pulse. The per-profile table below has each local pack's corresponding website factor and measured WAV gain range. The JavaScript uses `c1[id] ?? 1`; Blip, Glyph, and the local Mouse Snappy profile have no listed website factor. That fallback value is a code default for an unlisted ID, not a verified Keeby Mac trim. Mouse Snappy's Cream keyboard sources can be compared with the official Cream profile's `0.88` factor, but that does not establish an official Snappy factor.

In the normal `F7` key event path, the browser's `T` player starts a sample at gain `0.001` and ramps to the requested key gain over 3 ms. If a sample is longer than 40 ms, it holds that gain until 20 ms before the end, then ramps back to `0.001`. The path allows six simultaneous voices. When full, it fades the oldest voice to `0.001` over 10 ms and stops it at 15 ms. All key sounds pass through a `DynamicsCompressorNode` configured at threshold `-12 dB`, knee `6 dB`, ratio `4`, attack `2 ms`, and release `50 ms`. Normal key playback does not set `playbackRate` and does not attach a stereo panner. The helper `T` can accept an optional pan, but the normal `F7` down/up calls do not pass one; a separate profile-preview sequence does pass test pans.

`o0` routes Space to `space`, Enter and Numpad Enter to `enter`, Backspace and Delete to `backspace`, and other eligible keys to `alpha`. It returns no sound category for Shift, Control, Alt, Meta, Caps Lock, Escape, Tab, or arrow keys. The global handler also suppresses key repeats and tracks pressed keys so a release only plays for a key that had a matching down event. Eight current website profiles are explicitly blocked by the page's `Qr`/`G5` guard from the global typing path: IQUNIX MQ80, the three Flow 2 profiles, Akko CS Jelly Black, Akko V3 Pro Cream Yellow, Akko Clicky Pink, and Aflion Carrot. The remaining 14 are eligible. This is the browser code's behavior; it does not prove a Mac app chooser or runtime policy.

Brown uses a different website path. The `sound.ogg` sprite is decoded directly with `decodeAudioData`, without `Vi` or `B7`, then the browser selects per-code offsets and durations from its sprite maps. The local Brown config has 85 code pairs and 170 down/up definitions; it maps Fn (464), main Enter (28), but not keypad Enter (96), the numpad, or mouse buttons. Missing single-mode slices are silent; `sound.ogg` is not a fallback sound. Exact Brown slice offsets and durations are in [the checked config](../../scripts/keeby-web-keychron-k2-max-brown.json), SHA-256 `ae724987139b13fabc88dfed11a4066dcf944ff74a0d8ce8b46a9183c6d9591e`.

The website's tone-control preview (`v0`) is another separate path. It sets playback rate to `0.88 + 0.24 × toneY`; its low-pass cutoff is `-sampleRate/(2π) × ln(1 - max(0.06, toneX²))`, clamped to 80–20,000 Hz (or `min(20,000, sampleRate/2 - 100)` at toneX ≥0.99), with Q `0.5`. At toneX below `0.99`, the filtered path gain is `1 + (1 - toneX)² × 3` and a dry path is mixed at `(1 - toneX) × 0.45`. Its phase gains are `0.55 × c1` down and `0.4 × c1` up, multiplied by the user volume, with a `0.0001` floor and a 3 ms attack / 20 ms tail rule. These are preview settings only; the preview floor must not be confused with `F7`'s `0.001` floor or used to describe normal typing. A separate hero/profile preview uses `0.3 × c1` down and `0.2 × c1` up, schedules presses 200 ms apart and releases 70 ms later, and supplies test pans for Enter `+0.95`, Shift Left `-0.95`, G `-0.03`, `[` `+0.75`, and `/` `+0.8`. The page's global browser mouse handlers load `/sibat-down.wav` and `/sibat-up.wav` through `Vi`/`B7` and play them at `0.3`/`0.18`; this is distinct from keyboard-profile mouse assets.

## Linux 0.1.0-11 pre-fix path and likely mismatch

The pre-fix Linux loader shipped in package `0.1.0-11` read multi-pack files, made a base sample plus `0.92×` and `1.08×` pitch variants, and then called `normalize_pack_loudness`. That function finds one largest absolute PCM peak across every bank sample and applies `min(4, 0.9 / peak)` to the entire bank. `SampleMixer` selects among sample variants with a no-immediate-repeat rule, applies a random per-trigger gain in `[0.35, 0.65]`, multiplies by the existing `2×` master factor and the user volume, applies the Linux tone filter and stereo-width pan, sums voices, then clamps the output to `±0.8`. This is materially different from the website's per-file RMS correction and fixed down/up phase gains. The imported-WAV implementation under review also applies the verified F7-style attack and tail envelope. It does not add the website's `DynamicsCompressorNode` or reduce Linux's 32-voice pool (`kVoicePoolSize`) to the website's six-voice cap. Linux still applies user tone filtering and stereo-width pan when those controls are non-neutral; the website normal `F7` calls do not attach a tone filter or panner. These remaining differences mean exact output is not expected from the bounded fix.

The independent source audit finds low-level files next to high-peak files. Examples: Flow 2 Void's alpha WAVs have full-file RMS from `-51.82` to `-51.45 dBFS`; its source-bank peak is `0.895`, so the package 0.1.0-11 whole-bank calculation yielded only `1.005×`, while the website's per-WAV formula reaches its `16×` ceiling on the measured profile WAVs. Akko CS Jelly Black alpha is `-47.98` to `-44.43 dBFS`, also with a calculated package 0.1.0-11 whole-bank scale of `1.005×`; its website calculation reaches `16×`. These are source measurements and calculated gains, not measured runtime output or decibel comparison of final mixed audio.

This identifies an objective mismatch in the package 0.1.0-11 pre-fix playback path and a credible explanation for very quiet clips. It does not establish that the user's report was caused only by this mismatch. The website browser path applies different profile multipliers, envelopes, and compression; its default device, output chain, and runtime state are not captured here. The Mac app may use another path.

The cached 1.10.4 arm64 app contains symbols for `AppDelegate.perKeySound(...)`, `AppDelegate.bindPipeline` closures for both `KeyEvent` and a separate `MouseClickEvent`, `SwitchType.normalizationGain`, and types including `AudioEngine`, `SpatialAudioEngine`, `AVAudioEngine`, `AVAudioPlayerNode`, `AVAudioUnitVarispeed`, `AVAudioUnitEQ`, `AVAudioUnitDistortion`, and `AVAudioEnvironmentNode`. Strings and getters also expose names such as `_volume`, `masterGain`, `_spacebarVolume`, `_enterSoundVolume`, `_mouseClickVolume`, `_muteModifiers`, `mousePitchNode`, `enterPitchNode`, `enterTonePitch`, `mouseTonePitch`, and `decorrMaxGain`.

These names show that the native app has per-key, mouse, gain, pitch, and effect concepts. They do not reveal numeric values or exact runtime data flow. Static evidence did not establish native profile-to-key mappings, normalization formula, phase gain, envelope, compressor, pan, release behavior, event-repeat policy, or whether all resource folders appear in the chooser. The browser findings in this report are not a substitute for those unknown Mac values.

## Root cause and bounded change

The confirmed defect is the imported-bank normalization policy: a single per-bank sample peak cannot bring each quiet recording toward the website's per-file RMS target. The generated ±8% pitch variants and randomized per-trigger gain add more playback variation than the website's normal key path. This is a source-backed root cause for the processing mismatch; the audible symptom has not been reproduced or cleared by a listen test.

The merged change is limited to imported sound-pack rendering. It applies the verified per-WAV B7 RMS rule to native WAV clips; keeps the exact source clip without synthetic pitch variants or randomized gain; uses the verified website down/up gains and per-profile factors from the matrix; and leaves the Brown OGG sprite unnormalized, as the browser path does.
