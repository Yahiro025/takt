# Step 2.9: pacman packaging and autostart

## 1. Goal

Make KEEBY installable on the user's CachyOS machine as a normal pacman
package (`packaging/arch/PKGBUILD`), with a systemd user unit for autostart,
superseding the manual `scripts/install-keeby-inputd.sh` install from Step
2.5C/docs/006. The user runs `makepkg -si` and joins one group themselves;
nothing here runs automatically as root beyond the package's own install
scriptlet.

## 2. Install layout

| What | Dev build | Installed (package) |
|---|---|---|
| `keeby` | `build/*/keeby` | `/usr/bin/keeby` |
| `keeby-inputd` | next to `keeby` | `/usr/lib/keeby/keeby-inputd` |
| Built-in assets | `assets/` (source tree) | `/usr/share/keeby/assets/` |
| Fetch script | `scripts/fetch-mechvibes-packs.sh` | `/usr/bin/keeby-fetch-packs` |
| systemd user unit | -- | `/usr/lib/systemd/user/keeby.service` |
| Desktop entry | -- | `/usr/share/applications/keeby.desktop` |
| sysusers fragment | -- | `/usr/lib/sysusers.d/keeby.conf` |

Arch keeps private, non-PATH helper binaries under `/usr/lib/<pkg>/` rather
than `/usr/bin`, hence `keeby-inputd`'s location. Dev builds are unaffected:
`scripts/fetch-mechvibes-packs.sh` still works directly for anyone building
from source; `keeby-fetch-packs` is just its installed name.

## 3. Runtime path resolution

Two things used to be baked in at compile time via scattered
`target_compile_definitions(... KEEBY_ASSET_DIR="...")` on three separate
targets. Both are now resolved through a single small header,
`src/paths.hpp`:

- **Built-in assets** (`keeby::paths::asset_dir()`): `$KEEBY_ASSET_DIR` env
  var if set, else the compiled-in `KEEBY_ASSET_DIR_DEFAULT` macro, fed from
  a new `KEEBY_ASSET_DIR` CMake cache variable (default: the source `assets/`
  dir; the PKGBUILD sets `/usr/share/keeby/assets`). Used by `main.cpp` and
  `engine_controller.cpp`'s `"default"` profile fallback.
- **Helper path** (`resolve_helper_path()` in `src/input_capture.cpp`,
  unchanged structure, one added branch): `$KEEBY_INPUTD_PATH` override
  first (unchanged), then the compiled-in `KEEBY_HELPER_PATH_DEFAULT` macro
  if non-empty, fed from a new `KEEBY_HELPER_PATH` CMake cache variable
  (default: empty, meaning "resolve next to `keeby`'s own executable" --
  today's dev behavior, unchanged); the PKGBUILD sets it to
  `/usr/lib/keeby/keeby-inputd`.

Both cache variables default to exactly today's dev behavior, so an
un-configured `cmake -S . -B build` still works as before.

**Tests**: `sample_mixer_test` is untouched (it defines its own literal
`KEEBY_ASSET_DIR` macro and always tests directly against the source tree --
it never uses `paths.hpp`, deliberately left alone). `engine_controller_test`
does call the `"default"`-profile path via `set_profile("default")`, so it
needs real assets. In a dev build that's already the compiled default, but
during the package build's `check()` -- which runs *before* `package()`
installs anything to `/usr/share/keeby/assets` -- the compiled default
points at a directory that doesn't exist yet. Fixed with one
`set_tests_properties(engine_controller_test PROPERTIES ... ENVIRONMENT
"KEEBY_ASSET_DIR=${CMAKE_CURRENT_SOURCE_DIR}/assets")` in CMakeLists.txt,
forcing the real source tree regardless of the compiled default. Verified
live: `check()` inside `makepkg` (prefix `/usr`, both cache vars pointed at
their installed `/usr` paths) passed 12/12, including this test.

## 4. "Already running" exit code

`main()`'s single-instance guard (`docs/009` section 6) now returns `3`
instead of `1` when another `keeby` already owns the D-Bus name, so
`packaging/keeby.service`'s `RestartPreventExitStatus=3` can tell "another
instance is already running" (not a bug -- don't restart-loop) apart from a
real crash (any other nonzero exit -- do restart). No automated test covers
`main()`'s exit codes (it isn't linked into any test binary); this is a
one-line, compile-verified change, documented in `docs/009` section 6.

## 6. PKGBUILD: building from the working tree

The user's work past commit `0e0d8bd` (Step 2.2) is uncommitted, so a
git-`source=()` PKGBUILD would silently package stale code. Instead
`source=()` is empty and `_root="$startdir/../.."` points straight at the
repository root (`packaging/arch/../..`); `build()`/`check()`/`package()`
all reference `$_root` directly. `makepkg`'s default `src/`, `pkg/`, and the
`.pkg.tar.zst` output still land under `packaging/arch/` as usual (nothing
custom needed there); `packaging/arch/.gitignore` keeps all three out of the
git patch.

`build()` configures Release with `-DCMAKE_INSTALL_PREFIX=/usr
-DKEEBY_ASSET_DIR=/usr/share/keeby/assets
-DKEEBY_HELPER_PATH=/usr/lib/keeby/keeby-inputd`. `check()` runs `ctest`
(D-Bus tests self-SKIP via exit 77 with no session bus; PipeWire and the
input helper are faked in every test regardless). `package()` runs
`cmake --install` under `DESTDIR="$pkgdir"`, then `chown root:input` +
`chmod 2750` on the installed `keeby-inputd` (recorded by fakeroot, so no
real root is needed to build the package), then installs a license notice.

Dependencies were verified, not guessed: built both binaries, read
`readelf -d`'s direct `NEEDED` entries (not the full transitive `ldd`
closure), and mapped each to its owning package with `pacman -Qo`:
`libevdev`, `libsndfile`, `libpipewire` (the client library package --
distinct from the `pipewire` daemon package, since `keeby` only links the
former), `libsamplerate`, `sdbus-cpp`, `systemd-libs`, `glibc`, `gcc-libs`
(covers `libstdc++`/`libgcc_s`, split into separate packages on this
CachyOS snapshot but still resolved via the `gcc-libs` meta-package), plus
`acl` (`setfacl`, used by `keeby.install`, not linked). `makedepends`:
`cmake`, `ninja`, `nlohmann-json`. `checkdepends`: `python`
(`sample_variants_test`).

## 7. keeby.install: group creation order and ACL re-application

**Why a group, not the Step 2.5C single-user ACL.** Step 2.5C (docs/006
sections 39-45) granted execute on `keeby-inputd` to one hardcoded username
via `setfacl -m u:<user>:x`, applied by a manually re-run script. A PKGBUILD
scriptlet can't hardcode a username, and the user's actual decision for this
step was a dedicated `keeby` system group instead: anyone added to it can
run the helper (and therefore receive keystrokes through its socket --
same boundary as before, see docs/006 section 40), root and `input`-group
members still can too, and nobody else can. The user joins once
(`sudo usermod -aG keeby yahiro`, then reboot -- see section 12).

**Why `post_install`/`post_upgrade` call `systemd-sysusers` explicitly.**
pacman does run sysusers.d fragments automatically via its own hook -- but
that hook fires once, at the very end of the *entire* transaction, after
every package's own scriptlets have already run. `setfacl -m g:keeby:x`
inside this package's `post_install` would fail with "invalid group" if it
ran first. Calling `systemd-sysusers /usr/lib/sysusers.d/keeby.conf`
directly inside the scriptlet guarantees the group exists before the very
next line needs it.

**Why the ACL is re-applied on every upgrade, not just install.** pacman
replaces `keeby-inputd`'s file wholly on upgrade (a new inode), and a POSIX
ACL lives on the inode -- so any upgrade silently drops it otherwise, exactly
the class of gap Step 2.5C's section 39 already hit once with mode alone.
`post_upgrade` therefore just calls `post_install` again: re-run
`systemd-sysusers` (idempotent -- the group already exists), re-apply the
ACL, re-verify.

**Verification, not just application.** After `setfacl`, the scriptlet
checks `getfacl -p ... | grep -q '^group:keeby:--x$'` and
`stat -c %A ...`'s 7th character is `s`, printing a loud `*** ERROR ***` to
stderr for either failure -- mirroring `scripts/install-keeby-inputd.sh`'s
existing "never report success unless both checks pass" discipline, adapted
from a per-user to a per-group ACL entry. The exact `getfacl -p` text for a
group entry (`group:<name>:<perm>`) and the setgid-bit position in
`stat -c %A` (index 6) were both confirmed against a scratch file before
being hardcoded into the check.

**post_remove** is intentionally minimal: the `keeby` group is left in
place (harmless if unused elsewhere) with a printed, optional
`sudo groupdel keeby`.

## 8. Using it

Install/upgrade:
```sh
cd packaging/arch && makepkg -si
```
Then, once:
```sh
sudo usermod -aG keeby yahiro   # reboot afterwards -- see section 12
systemctl --user enable --now keeby.service
```
`keeby-fetch-packs` fetches community sound packs (same script as
`scripts/fetch-mechvibes-packs.sh`, just on `PATH` now); also linked from
the tray's "Switch sound" submenu hint when only the built-in pack exists.

Autostart control: `systemctl --user disable --now keeby.service` to stop
autostarting (or just `stop`/`start` for one session); `keeby ctl ...` from
a terminal or a niri keybinding works whether or not it's a service.

**Migrating from the manual install** (`scripts/install-keeby-inputd.sh`,
docs/006): `post_install`/`post_upgrade` detect a leftover
`/usr/local/bin/keeby-inputd` and print a reminder to run
`sudo ./scripts/uninstall-keeby-inputd.sh`. Nothing removes it
automatically -- `keeby`'s own `resolve_helper_path()` prefers
`$KEEBY_INPUTD_PATH` if set, then the compiled `/usr/lib/keeby/keeby-inputd`
default, so the packaged install works correctly even if the old copy is
left behind; removing it is just hygiene, not required for correctness.

Verify the install:
```sh
ls -l /usr/lib/keeby/keeby-inputd     # expect -rwxr-s---+ root input (trailing + = ACL)
getfacl /usr/lib/keeby/keeby-inputd   # expect group:keeby:--x
id                                     # expect 'keeby' in your groups, after rebooting
systemctl --user status keeby
journalctl --user -u keeby
```

Uninstall: `sudo pacman -Rns keeby` (the `keeby` group is left behind; see
section 7).

## 9. Security model (current state)

Unchanged from docs/006's core design: `keeby-inputd` is the only process
that opens `/dev/input/*`, installed `root:input` mode `2750`, not setuid,
no capabilities. What changed in this step is *how* execute access beyond
`root`/`input` is granted: a re-appliable group ACL instead of a one-time,
hardcoded-username manual script. Exactly who can execute the helper (and
therefore receive keystrokes through its socket -- the real boundary, see
docs/006 section 40) after this step: `root`, members of `input`, and
members of `keeby`. Residual risks are the same ones docs/006 section 43
already disclosed and are not re-litigated here: any process running as the
same UID as a `keeby`-group member can execute the helper directly, and
none of this sandboxes `keeby` itself.

## 12. Why a reboot, not a logout (2026-09-25 fix, pkgrel 2)

Verified live on the user's machine: the package installed correctly (ACL,
setgid, and the `keeby` group present with the user as a member), but
`keeby.service` looped forever with "not executable by this user
(Permission denied)" -- the restart counter passed 15. The user had joined
the `keeby` group and had logged out and back in; it still failed.

Root cause: `loginctl show-user $USER -p Linger` was `yes`. Lingering keeps
the systemd `--user` manager (and everything it starts, including
`keeby.service`, and on some setups the whole graphical session) running
across a logout, so a mere relogin never gives it fresh groups -- it keeps
the supplementary groups it had when it was originally started, from
*before* `usermod -aG keeby` ran. Only restarting the user manager itself
picks up the change. A reboot always does this; from a text console (not
the graphical session itself), `sudo systemctl restart user@<uid>.service`
also works but ends the whole graphical session, since everything in it is
a child of that manager.

Check whether this applies to you:
```sh
loginctl show-user $USER -p Linger
grep Groups /proc/$(pgrep -u $USER -xo systemd)/status
```
`Linger=yes` means logging out will not help. The second command prints
the user manager's own numeric supplementary groups -- cross-check the
`keeby` group's gid (`getent group keeby`) against that list; if it is
missing there despite `id` (a fresh command) showing `keeby`, this is the
same issue, and a reboot, not a relogin, is required.

Because of this, every "log out and back in" instruction for the `keeby`
group -- in this document, `keeby.install`'s printed next steps, and
`input_capture.cpp`'s own startup error message -- now says "reboot"
instead. `input_capture.cpp`'s `access(X_OK)` failure in `start()` also
gained a precise diagnosis for exactly this case: if the account is listed
in `/etc/group`'s `keeby` line (`getgrnam`'s `gr_mem`) but that gid is
absent from this process's own `getgroups()`, the error names the cause
directly ("you are in the 'keeby' group, but this process started before
you joined it") instead of repeating the generic two-remedy message.
Verified live in this exact machine state (`Linger=yes`, `keeby` gid
missing from the running user manager's groups): `input_capture_test`'s
existing non-executable-helper case exercises this branch for real and
produces exactly that message.

## 13. Start limit: giving up instead of looping forever (2026-09-25 fix, pkgrel 2)

Live evidence from the same install: with only `RestartSec=2` set, the
default start-rate limit (5 starts per 10s) never tripped, so
`keeby.service` restarted forever against the group/reboot problem above --
spamming the journal indefinitely instead of surfacing a clear failure.
`packaging/keeby.service` now sets an explicit limit in `[Unit]`:

```ini
StartLimitIntervalSec=60
StartLimitBurst=5
```

After 5 start attempts inside 60 seconds, systemd stops restarting and
leaves the unit `failed` instead of retrying forever --
`systemctl --user status keeby.service` then shows the real failure
instead of an endless retry loop. Once the underlying cause is fixed (e.g.
the reboot above), clear the failed state before starting again:
```sh
systemctl --user reset-failed keeby.service
systemctl --user restart keeby.service
```
Verified with `systemd-analyze verify --user` against a copy of the unit
with `ExecStart` pointed at the real built binary (same technique as
section 10): passes cleanly, no diagnostics.
