# Step 2.6: sound engine v2 (every key, press+release, stereo pan)

Goal (from the supervisor brief): every key on a standard keyboard makes a
sound on press; key release makes a quieter/different sound (auto-repeat
stays silent); each sound is panned by the key's physical left/right
position with a global stereo-width control; the data model is generic
enough for Step 2.7 to load arbitrary per-key sound packs and swap them at
runtime (not implemented here -- no pack files, no discovery, no runtime
switching in this step).

## Data model

`SoundBank` (src/sample_mixer.hpp) replaces the old fixed 2-category model:

```cpp
struct KeySound { uint16_t first = 0; uint8_t count = 0; }; // count==0 -> silent
struct SoundBank {
    std::vector<Sample> samples;                 // all PCM, owned outside the RT path
    std::array<KeySound, kKeyCodeCount> press{};  // kKeyCodeCount = 465; supported slots are sparse
    std::array<KeySound, kKeyCodeCount> release{};
    std::array<float, kKeyCodeCount> pan{};       // [-1, 1], 0 = center
};
```

This is intentionally pack-agnostic: nothing in `SoundBank`, `SampleMixer`, or
`validate_sound_bank` assumes samples are shared across keys. The built-in
default bank (`load_default_bank`, src/sample_mixer.cpp:75-100) happens to
point every key's press range at one of two shared 3-variant ranges (the
regular click, or a deeper one for big keys) and every key's release range at
one shared placeholder range, but a Step 2.7 pack with a unique sample per
key is exactly as valid a `SoundBank` -- it would just fill `samples` more
densely and give every key its own non-overlapping `KeySound`.

`validate_sound_bank` (src/sample_mixer.cpp:53-64, off-RT) checks: every
sample's PCM is finite, in [-1, 1], stereo-aligned, and 1..480000 frames
(tightened from Step 2.2-2.4: an empty `Sample` used to be an allowed "hole"
marking an absent category slot; that concept is gone now that absence is
`KeySound{count=0}`, so `valid_pcm` now rejects empty PCM outright); every
non-empty press/release range's `first + count` is in bounds for `samples`;
every pan is finite and in [-1, 1]. `SampleMixer`'s constructor calls it and
throws `std::invalid_argument` on failure, same startup-only contract as
before.

## RT behavior

`SampleMixer::handle_event` (src/sample_mixer.cpp:161-167) dispatches
Down/Up to a shared `trigger()` helper against the press/release range and
that key's own last-played-variant slot; Repeat and out-of-range/zero codes
are rejected before any array is touched; disabled state is checked once
before dispatch, so disabling suppresses both press and release triggers
identically. `trigger()` (src/sample_mixer.cpp:125-159) is effectively the
old algorithm parameterized over which range/history array it's called
with: unchanged xorshift32 PRNG, unchanged "exclude the last variant, no
rejection loop" selection, unchanged gain-range randomization -- so for a
fixed seed the sequence of random draws per Started trigger (one for variant,
one for gain) is bit-identical to Step 2.2-2.4's, which is why the golden
`test_variation` constants could be kept unchanged (see Tests).

New in `trigger()`: pan/width -> per-channel gain. `width` is loaded once per
trigger (a relaxed atomic, same pattern as `master_gain_`); `pan =
clamp(bank_->pan[code] * width, -1, 1)`; `gain_l = gain * min(1, 1 - pan)`,
`gain_r = gain * min(1, 1 + pan)`. At pan == 0 this reduces to
`gain_l == gain_r == gain`, i.e. byte-identical to the old single-gain
behavior -- confirmed by every pre-existing numeric assertion in
`test_mix`/`test_pool_and_clamp`/`test_enable_and_master_gain` passing
unchanged (those test banks never set `pan`, which defaults to 0 for every
key). Each channel only ever attenuates (the `min(1, ...)` term is <= 1), so
a hard-panned key's near channel plays at exactly the trigger's own gain,
never louder.

Per-key history (`last_press_variant_`/`last_release_variant_`,
`std::array<uint8_t, kKeyCodeCount>` with 465 entries, sentinel `0xff` =
"no prior variant") is indexed
by the raw key code, not by the sample range it happens to point at. Two keys
sharing the same `KeySound` (as most keys do in the default bank) therefore
get independent no-immediate-repeat guarantees -- see
`test_per_key_variant_history`, which proves both that a single key never
repeats itself and that a second key sharing its range is free to (and, over
200 draws, does) pick the same variant the first key just played.

`SampleMixer::mix` (src/sample_mixer.cpp:170-196) is unchanged except that
the per-voice scalar `gain` became `gain_l`/`gain_r`, applied to output
channel 0/1 respectively (both multiplied by `master` as before, one load
per callback). `Voice` (src/sample_mixer.hpp) gained a second float
(`gain_l`, `gain_r` replacing one `gain`); no new allocation, still
trivially destructible, still a fixed 32-slot array.

## Bank ownership and the RT pointer indirection

`SampleMixer` stores the bank by value in `bank_storage_` and reads it
everywhere else through `bank_`, a `const SoundBank* const` set once in the
constructor's initializer list (src/sample_mixer.hpp:126-135,
src/sample_mixer.cpp:106-113). This is safe because `SampleMixer` is
already permanently non-movable: its copy operations are explicitly
deleted, and its `std::atomic<bool>`/`std::atomic<float>` members make any
compiler-generated move ill-formed too, so the compiler defines none. That
guarantees `bank_storage_` never relocates for the lifetime of the object,
so `bank_` never dangles -- with today's single, fixed-at-construction bank
this indirection is otherwise a no-op. It exists purely so Step 2.7 can
later change `bank_`'s declaration to an atomically-swapped pointer to an
externally-owned bank without touching `trigger()`, `handle_event()`, or
`mix()` at all.

**What Step 2.7 still has to handle when it adds the swap:** `Voice::data`
(src/sample_mixer.hpp) is a raw `const float*` taken directly from
`bank_->samples[...].pcm.data()` at trigger time (src/sample_mixer.cpp:155).
A voice does not hold a reference to the bank it came from, only that raw
pointer plus a frame count. If Step 2.7 swaps `bank_` to point at a new bank
while old voices from the previous bank are still playing, and then destroys
the old bank, every such voice's `data` pointer dangles on the very next
`mix()` call -- this is a real, silent use-after-free, not merely stale
audio. Step 2.7's swap must keep every previously-active bank alive until
`mix()` has retired (or forcibly stopped) every voice that was triggered
against it, e.g. by refcounting banks and having the RT side drop its last
reference only from the (single-writer) audio thread itself, or by only ever
freeing an old bank after a full voice-pool drain has been observed from
that same thread. A second, smaller item: `last_press_variant_`/
`last_release_variant_` are sized and indexed by raw key code, independent
of any particular bank's contents, so they need no special handling across a
swap -- a history entry simply becomes "stale" (referring to a variant index
that may mean something different in the new bank) for one trigger, which is
cosmetic, not unsafe, since `count` is always re-read from the *new* bank's
`KeySound` before the index is used.

## Physical key-layout / pan table

`src/key_layout.hpp`: `key_x(code)` is a `constexpr` `switch` mapping evdev
`KEY_*` codes to a horizontal position, `key_pan(code) = (2*key_x(code) - 1)
* 0.5`. Revised after the first review pass: the user's machine is a laptop
(no numpad), so the normalization centers on the *main alphanumeric block*
(function row, number row, all letters/punctuation, all modifiers, Space,
Enter, Backspace) rather than a full 104-key footprint -- `x = unit_center /
15` puts the main block exactly on [0, 1] and pan exactly on [-0.5, 0.5]
(`stereo_width`, clamped to [0, 2], has headroom to widen that up to the
full [-1, 1] `SoundBank::pan` range). The nav cluster (arrows, Ins/Del/Home/
End/PgUp/PgDn, PrtSc/ScrLk/Pause) and numpad are extra, further right, at
x in [1.05, 1.20] and [1.25, 1.45] respectively -- `key_x` is deliberately
not bounded to [0, 1] globally, only across the main block that every
keyboard has; `validate_sound_bank` still holds (max pan is 0.95, inside
[-1, 1]). This is a standard-key-unit model (1u = one letter-key width), not
a mm-accurate CAD layout. Coverage: Esc, F1-F12, the full number row, all 26
letters, all number-row/punctuation symbols (`-=[]\;',./` and grave),
Tab/Caps/both Shifts/both Ctrls/both Alts/both Supers/Menu, Space/Enter/
Backspace, all four arrows, Insert/Delete/Home/End/PageUp/PageDown,
PrintScreen(SysRq)/ScrollLock/Pause, and every numpad key (NumLock through
KP Enter, including the 2-wide KP0). Unlisted codes (including 0) fall
through to x = 0.5, i.e. pan 0.

Representative pan values (default width 1.0):

| Key | pan | | Key | pan |
|---|---|---|---|---|
| Esc | -0.467 | | P | +0.233 |
| Q | -0.367 | | Enter | +0.425 |
| A | -0.350 | | Backspace | +0.433 |
| Space | -0.042 | | Up (nav) | +0.625 |
| G | -0.083 | | KP5 (numpad) | +0.825 |
| H | -0.017 | | | |

`test_pan` asserts thresholds on these (`|pan(Space)| < 0.1`, `pan(Q) <
-0.25`, `pan(P) > 0.15`, `pan(Enter) > 0.3`, numpad > nav cluster >
main-block right edge) rather than exact magnitudes.

## Default bank (Step 2.6 placeholder pack)

`load_default_bank(directory)` (src/sample_mixer.cpp:66-100): loads 9
samples total (click_down/_low/_high, click_up/_low/_high, release/_low/
_high). Every key 1..255 presses with the click range and releases with the
release range; `KEY_SPACE`, `KEY_ENTER`, `KEY_KPENTER`, and `KEY_BACKSPACE`
override their press range to the click_up ("deep") range. Code 0 is left
untouched (`KeySound{}`, silent), matching `handle_event`'s hard rule that
code 0 is never triggered. Pan is `key_pan(code)` for every key 1..255.

`assets/generate_variants.py` now also derives `release.wav` from
`click_down.wav` (not a recording): truncate to the first ~40 ms, apply a
per-channel first-difference high-pass (`y[n] = x[n] - x[n-1]`, turning the
low "thock" into a brighter tick), normalize to ~-10 dB relative to
`click_down.wav`'s own peak (verified: 916/2897 = 0.3162 = 10^(-10/20)
exactly), fade the last quarter out to avoid a truncation click, then derive
`release_low.wav`/`release_high.wav` from *that* via the same 0.92/1.08
interpolation as every other pitch variant. `--check` now covers all seven
generated files (the four Step 2.3 variants plus the three release files).
These are explicitly documented in assets/README.md as placeholders to be
replaced wholesale by recorded release samples in Step 2.7.

## Limitations / explicitly out of scope

- No pack files, pack discovery, or runtime pack switching -- Step 2.7's job.
- `key_layout.hpp` models a standard ANSI main block (+ optional nav cluster/
  numpad) only; no ISO/split variants, and ties (e.g. all numpad-row-1 keys)
  share one x per column rather than modeling exact key widths.
- The release samples are synthesized placeholders, explicitly documented as
  such in assets/README.md, not recorded release sounds.
- `stereo_width` has no smoothing/ramping -- like `master_gain`, a change
  applies to the next trigger, not to already-playing voices (consistent
  with how `master_gain` already behaves, applied once per `mix()` callback).
