# Step 2.4: minimal desktop shell

## 1. Goal

Wrap the existing Step 2.1-2.3 real-time engine in the smallest usable
desktop shell: start/stop lifecycle, a system-tray status item (Wayland/Niri-
compatible), enable/disable, one master-volume control, and quit — without
touching the audio callback's real-time guarantees or the mixer/pitch
algorithm.

## 3. Selected desktop technology and why

**sdbus-c++** (systemd's `sd-bus` with an idiomatic modern-C++ API),
implementing the **StatusNotifierItem** D-Bus protocol directly — no GTK,
Qt, or libappindicator.

- **Wayland/Niri**: Niri does not implement a native systray (no
  compositor-side tray protocol exists in the Wayland core or wlr
  protocols). The de facto standard on Wayland — same as on X11 desktops
  that dropped the old XEmbed tray — is StatusNotifierItem/AppIndicator: an
  application exports a small D-Bus object and *any* compatible status-bar
  panel renders it. This is a bus protocol, not a compositor protocol, so it
  needs nothing Niri-specific.
- **System tray/status notifier expectations**: implementing the protocol
  directly (methods `Activate`/`SecondaryActivate`/`Scroll`/`ContextMenu`,
  properties `Category`/`Id`/`Title`/`Status`/`IconName`/`ItemIsMenu`) means
  KEEBY works with *any* StatusNotifierItem host — Waybar, KDE's systray,
  or (as verified live on this machine) a quickshell-based bar — without
  hard-coding to one.
- **C++ integration**: sdbus-c++ 2.3.1 is already installed
  (`pkg-config sdbus-c++`) and gives a declarative, exception-based API
  (`registerMethod(...).implementedAs(lambda)`,
  `registerProperty(...).withGetter(lambda)`) that fits this codebase's
  existing C++23/RAII style far better than the C GObject API GTK or
  libappindicator would require.
- **Build complexity / dependency size**: sdbus-c++ links only
  `-lsdbus-c++ -lsystemd`. GTK3 (for libappindicator) or Qt (for a
  QSystemTrayIcon-based approach) would each pull in an entire widget
  toolkit, a font/rendering stack, and (for GTK) GLib/GObject — a large,
  unjustified addition for "one tray icon with three actions."
- **Maintainability**: the whole tray surface is ~110 lines in
  `tray_service.cpp`, reviewable in one sitting, with no generated bindings,
  no meta-object compiler step, and no GUI event loop to reconcile with the
  engine's own threads.

Documented distinction per the task's requirement: **Niri itself provides no
tray.** A compatible host must be running and watching
`org.kde.StatusNotifierWatcher` (Waybar is the common choice on Niri; on
this development machine a quickshell-based shell already owns that name —
see section 14). KEEBY implements the standard protocol only; it does not
special-case Niri or any particular host.

## 4. Architecture

```text
Desktop Shell (TrayService, D-Bus)
     |
     | EngineController::set_enabled / set_master_gain (atomic stores)
     v
EngineController                       <- new, Step 2.4
     |
     +--> KeyEventTransport
     |
     +--> AudioBoundary  --owns-->  SampleMixer (atomic enabled_/master_gain_)
     |
     +--> InputCapture
```

`EngineController` is the only thing `main()` and `TrayService` talk to; it
never exposes `pw_stream*`, `libevdev*`, or the transport directly. It is a
thin RAII owner (construct -> `start()` -> `stop()`/destructor), not a new
subsystem — the same shape `AudioBoundary`/`InputCapture` already have.
`TrayService` never touches `AudioBoundary`, `SampleMixer`, or PipeWire; it
only calls `EngineController`'s four control methods, which are themselves
one-line atomic forwards down to `SampleMixer`.

## 5. Lifecycle model

`EngineController::start(device_path)`:
1. `AudioBoundary::start(transport_)` — same as Step 2.1-2.3.
2. `InputCapture::start(device_path, transport_)` — same as before.
3. If step 2 fails, step 1 is rolled back (`audio_.stop()`) before returning
   the error, so a failed `start()` never leaves a half-running engine.

`stop()` calls `capture_.stop()` then `audio_.stop()`, matching the existing
shutdown order in `main.cpp`. Both are idempotent (verified by
`engine_controller_test`), and the destructor calls `stop()` unconditionally
(RAII), so an `EngineController` going out of scope — or a `TrayService`
callback requesting quit — can never leak the thread/PipeWire/evdev
resources it owns.

`TrayService::start()`/`stop()` follow the same shape: `start()` connects to
the session bus, publishes the object, and (best-effort) registers with the
watcher; `stop()` tears down the exported object and the connection.
`main()`'s shutdown order is `tray.stop(); engine.stop();` — the tray goes
first so no D-Bus call can reach a controller mid-teardown.

## 6. Thread model

- **PipeWire RT thread** (unchanged from Step 2.1): runs `AudioBoundary::process()`.
- **InputCapture thread** (unchanged): reads evdev, pushes into the transport.
- **sdbus-c++'s internal dispatch thread** (new): started by
  `connection_->enterEventLoopAsync()` inside `TrayService::start()`.
  Handles incoming `Activate`/`SecondaryActivate`/`Scroll`/`ContextMenu`
  calls. Each handler does at most one atomic store (via
  `EngineController`) and, for quit, invokes a `std::function<void()>`
  supplied by `main()`.
- **Main thread** (unchanged shape): owns everything, polls `g_running`
  every 500 ms, same as Step 2.1-2.3's Ctrl+C handling. The tray's quit
  handler sets the *same* atomic `g_running` a `SIGINT`/`SIGTERM` handler
  would — quitting from the tray and quitting from the terminal are the
  same code path from that point on.

No new thread touches PipeWire, evdev, or the transport. The D-Bus thread
only ever writes `SampleMixer`'s two atomics through `AudioBoundary`'s
forwarding methods.

## 7. Enable/disable implementation

`SampleMixer` gained `std::atomic<bool> enabled_{true}` (verified
`is_always_lock_free` via `static_assert`, same pattern as
`AudioBoundaryCounters`). `handle_event()` now returns `Ignored` immediately
if `!enabled_.load()`, checked right after the existing
`kind != Down` check and *before* the key-code switch — so it behaves like
any other rejected event: **no PRNG/variant-history mutation**, matching
Step 2.3's existing invariant that only accepted triggers advance state.

**Design choice**: disabling suppresses only *new* voice triggers.
Currently-playing voices finish naturally (no abrupt cutoff, no extra
per-voice teardown code). Keyboard input capture and the PipeWire stream
both keep running unchanged — no repeated PipeWire/evdev teardown just to
mute the app, per the task's own guidance to minimize state transitions in
expensive subsystems. Re-enabling is a single atomic store; there is no
"paused" intermediate state to reconcile.

## 8. Master-volume implementation

`SampleMixer` gained `std::atomic<float> master_gain_{1.0f}`. `set_master_gain()`
clamps to `[0.0, 1.0]` with `std::clamp` before storing — 0.0 = silent,
1.0 = normal configured (Step 2.3) volume, never amplified beyond it.

Applied in `mix()`: one relaxed atomic load *per callback* (not per sample —
a volume knob has no reason to track finer than one ~85 ms/4096-frame
window), then `const float gain = voice.gain * master;` per active voice
before that voice's sample loop. This is exactly
`effective_gain = randomized_voice_gain * master_gain` from the task spec,
applied predictably in the existing mixing pipeline, leaving the Step 2.3
per-trigger randomized-gain distribution (`[0.35, 0.65]`) completely
unmodified — master gain is a second, independent multiplier, not a change
to that range.

## 9. Profile handling

Only one profile exists (the `SampleBank` loaded at startup from
`KEEBY_ASSET_DIR`). `EngineController::available_profiles()` returns
`{"default"}`, `profile()` reports it, and `set_profile(name)` returns
`true` only for that exact name — deliberately not a profile-loading
subsystem. The tray's `Title` property includes `(default)` so the current
profile is visible. Extending this to real multi-bank switching later means
adding bank storage/reload logic here; the interface shape does not need to
change.

## 10. Real-time safety audit

Audited every call reachable from `AudioBoundary::process()` after the
Step 2.4 changes, focused on the new control-state reads:

| Concern | Reachable from the RT callback? |
|---|---|
| heap allocation / deallocation | No |
| mutexes / condition variables | No |
| filesystem access | No |
| GUI calls | No — `TrayService`/sdbus-c++ objects are never referenced by `AudioBoundary`, `SampleMixer`, or anything they call |
| IPC that can block | No — no D-Bus call, socket, or pipe is reachable from `process()`; the only cross-thread reads are the two atomics |
| logging | No |
| process spawning | No |
| arbitrary container growth | No |
| sleeps / waits / blocking syscalls | No |

Desktop state crosses into the audio engine as two `std::atomic` members of
`SampleMixer` (`enabled_`, `master_gain_`), each `static_assert`ed
lock-free. The RT thread only ever *reads* them
(`std::memory_order_relaxed`); the D-Bus dispatch thread only ever *writes*
them, via `EngineController::set_enabled`/`set_master_gain` ->
`AudioBoundary::set_enabled`/`set_master_gain` -> `SampleMixer`'s setters.
No lock, no blocking wait, no GUI object is ever touched by
`AudioBoundary::process()`, `SampleMixer::handle_event()`, or
`SampleMixer::mix()`.

Updated worst-case per-callback bound (additive to Step 2.3's existing
bound in `docs/004-step-2.3-sound-fidelity.md`):
- `handle_event()`: **+1** relaxed atomic load of `enabled_` per accepted
  event (<=32 events/callback => <=32 extra loads).
- `mix()`: **+1** relaxed atomic load of `master_gain_` per callback, plus
  **+1** multiply per active voice (<=32) to fold it into that voice's gain
  before the existing per-sample multiply-add loop — no change to the
  per-sample inner-loop cost itself.

This remains an operation-count bound, not a hard real-time deadline — the
same caveat from Step 2.1-2.3 about OS scheduling, paging, and PipeWire's
own behavior still applies, unchanged.

## 14. Wayland/Niri findings

- Niri (`niri msg version` -> 26.04) exposes no compositor-level tray; this
  is expected and consistent with upstream Niri, which does not implement a
  systray protocol (there isn't a standard Wayland-core or wlr-protocols
  tray surface for a compositor to implement in the first place — tray
  icons are a D-Bus-level convention among status-bar applications, not a
  compositor feature).
- On this development machine, `org.kde.StatusNotifierWatcher` and
  `org.kde.StatusNotifierHost-*` are already owned by a running
  **quickshell** (`qs`) process — a Wayland shell/bar toolkit the user has
  configured, not something this task installed or assumes. This is what
  let `RegisterStatusNotifierItem` succeed and be verified live above.
  Whether `qs`'s configuration actually *renders* KEEBY's icon visually was
  **not** verified by me (I have no way to see the screen); that is a
  protocol-level pass, not a rendered-pixel pass, and is part of what's
  being handed to you.
- **Waybar** was checked and is not installed (`which waybar` -> not found)
  on this machine. KEEBY does not require Waybar specifically — any
  StatusNotifierItem-host-capable bar (Waybar, quickshell with a
  `SystemTray` component, etc.) works, since KEEBY implements the standard
  protocol and does not special-case any one host.
- If a person runs KEEBY on a Niri session with **no** StatusNotifierWatcher
  host running at all, `TrayService::start()` still succeeds (session bus
  connection + object publication), the `RegisterStatusNotifierItem` call
  fails, a warning is printed to stderr, and the engine keeps running
  normally without a visible tray — this is the documented, tested-by-code
  fallback (see `tray_service.cpp`'s catch block), though the "no host at
  all" branch itself was not separately exercised live in this session
  since a host happens to already be running here.

## 15. Known limitations

- No dbusmenu/right-click context menu is implemented. Controls are:
  left-click (`Activate`) toggles enable, scroll (`Scroll`) adjusts volume
  in 5% steps, middle-click (`SecondaryActivate`) quits. `ContextMenu` is a
  no-op. This was a deliberate minimalism choice (see section 3) — some
  hosts that only show a menu on click, with no scroll/middle-click
  affordance surfaced to the user, will make these controls hard to
  discover even though they work.
- No dynamic icon: the tray icon is always `input-keyboard`; enabled/
  disabled/volume state is conveyed only through the `Title` text (and a
  `NewTitle` signal on change), not a different icon or badge.
- `ItemIsMenu` is `false` and no `Menu` object/property is published.
- Volume steps are a fixed 5% per scroll tick; there is no fine-grained
  drag/slider control (no widget to drag — this is a protocol-level item,
  not a GUI).
- Master gain changes apply per `mix()` callback (~85 ms at 4096 frames),
  not per-sample — an intentional simplification (see section 8), not a
  measured audible artifact.
- `EngineController::set_profile` only ever accepts the single loaded
  profile name; there is no profile-switching (bank-reload) logic yet.
- The tray's registration-failure path (no watcher present at all) is
  exercised by code (try/catch, non-fatal, stderr warning) but was not
  separately live-tested in this session, since a watcher happens to
  already be running on this development machine.
